# 哈夫曼树（权值最小的两棵先合并）

> 对应程序：[HuffmanTree.java](./HuffmanTree.java)
> 编码那一步单独一篇：[哈夫曼编码.md](../huffmancode/%E5%93%88%E5%A4%AB%E6%9B%BC%E7%BC%96%E7%A0%81.md)。本篇只管"怎么把这棵树建出来"。
> 下文所有输出都是本机（JDK 21）实跑 `main` 拿到的。

---

## 一、要解决的问题：带权路径长度最短的二叉树

一棵二叉树里，某个节点的**路径长度** = 它到根经过的边数（根算第 0 层）。给它一个权值 `w`，就有**带权路径长度 WPL**：

```
WPL = Σ (叶子权值 × 叶子层数)
```

给定一组权值，怎么搭树能让 WPL 最小？直觉就两条：**权值大的离根近，权值小的离根远**。哈夫曼算法把它变成可执行的贪心：

> **每次从森林里挑出权值最小的两棵，合并成一棵（新根权值 = 两者之和），再放回森林；重复到只剩一棵。**

`main` 用的权值组是 `{13, 7, 8, 3, 29, 6, 1}`，实测：

```
原始nodes = [Node{value=1}, Node{value=3}, Node{value=6}, Node{value=7},
             Node{value=8}, Node{value=13}, Node{value=29}]
最终赫夫曼树 = Node{value=67}
67 29 38 15 7 8 23 10 4 1 3 6 13      ← preOrder 的输出
```

根是 67（= 1+3+6+7+8+13+29，所有叶子的权值和，这个必须是它）。

---

## 二、按前序输出把树还原出来

前序 `67 29 38 15 7 8 23 10 4 1 3 6 13`，配合"叶子是原始权值、非叶子是合并和"这条规则，树长这样：

```
                     67
                   /    \
             (29)叶      38
                       /   \
                     15     23
                    /  \    /  \
                (7)叶 (8)叶 10  (13)叶
                            /  \
                        (6)叶   4
                               / \
                           (1)叶 (3)叶
```

**每层合并的顺序**（对应代码 while 循环每一轮）：

| 轮次 | 取出的最小两个 | 新节点 | 放回后森林（已排序） |
|---|---|---|---|
| 1 | 1 + 3 | 4 | 4 6 7 8 13 29 |
| 2 | 4 + 6 | 10 | 7 8 10 13 29 |
| 3 | 7 + 8 | 15 | 10 13 15 29 |
| 4 | 10 + 13 | 23 | 15 23 29 |
| 5 | 15 + 23 | 38 | 29 38 |
| 6 | 29 + 38 | **67** | 67 → 结束 |

WPL 按定义算：`29×1 + 7×3 + 8×3 + 13×3 + 6×4 + 1×5 + 3×5 = 157`。

**一条省事的验算**：WPL 等于**所有非叶子节点权值之和** —— `4+10+15+23+38+67 = 157` ✅ 两种算法对上，说明这棵树确实按预期建出来了。（道理：每个叶子被"背"上去的次数正好等于它的层数。）

## 三、代码：`Node` 为什么要实现 `Comparable`

```java
class Node implements Comparable<Node> {
    int value; Node left; Node right;
    @Override public int compareTo(Node o) { return this.value - o.value; }   // 从小到大
}
```

整个算法只依赖一个动作："把最小的两个挑出来"。这份实现用的是**每轮重新 `Collections.sort(nodes)` 然后取 `get(0)`、`get(1)`**：

```java
while (nodes.size() > 1) {
    Collections.sort(nodes);                       // ← 每一轮都整体排序
    Node leftNode = nodes.get(0), rightNode = nodes.get(1);
    Node parent = new Node(leftNode.value + rightNode.value);
    parent.left = leftNode; parent.right = rightNode;
    nodes.remove(leftNode); nodes.remove(rightNode);
    nodes.add(parent);
}
```

三个值得记的点：

1. **`parent` 只有权值、没有原始数据**（`left`/`right` 才挂着数据）。所以哈夫曼树里"信息全在叶子，非叶子只是骨架"——这也是下一篇生成编码表时只遍历叶子的原因。
2. **`nodes.remove(leftNode)` 是按对象移除**，不是按下标。因为刚排完序，`get(0)`/`get(1)` 的下标一旦 remove 就变了，先拿引用再按引用删是对的写法；写成 `remove(0); remove(1)` 就会删错（第二个删到了原来的第三位）。
3. **`compareTo` 用 `this.value - o.value`**：权值场景安全（都是正的小整数），但这是通用的减法比较，理论上会溢出 —— 权值可能很大时应写 `Integer.compare(this.value, o.value)`。

### 代价：`Collections.sort` 每轮都来一次

n 个权值要合并 n-1 轮，每轮排一次 `ArrayList`：

| 做法 | 总代价 |
|---|---|
| 本篇：每轮 `Collections.sort` | **O(n² log n)** |
| 用 `PriorityQueue`（小顶堆）：每轮 `poll` 两次 + `offer` 一次 | **O(n log n)** |

n = 7 时看不出差别，权值上万就是天壤之别。**"每次取最小两个"这个需求就是优先队列的教科书场景**（正好接上 [堆排序.md](../tree/%E5%A0%86%E6%8E%92%E5%BA%8F.md) 第八节第 1 条）。

## 四、⚠️ 哈夫曼树不唯一，编码也不唯一

同一组权值，可能建出形态不同、WPL 却相同的树，原因有三个：

1. **权值相同的节点谁先谁后没有规定**。上面第 3 轮 `7` 和 `8` 合并成 `15`，第 4 轮 `10` 和 `13` 合并成 `23`，第 5 轮才是 `15 + 23`；如果并列权值的相对顺序变了，父子关系就会变。
2. **左孩子 / 右孩子谁放小的也没有规定**（本篇是"左小右大"：`parent.left = 最小的那个`）。
3. 下一篇的编码表还会把"左 0 右 1"这个约定叠加进来（反过来用 左1右0 也合法）。

**后果很实际**：压缩端解压端必须用**同一棵树**（或同一张编码表），否则解出来是乱码。这就是哈夫曼压缩必须把编码表随数据一起存的原因，也是 [哈夫曼编码.md](../huffmancode/%E5%93%88%E5%A4%AB%E6%9B%BC%E7%BC%96%E7%A0%81.md) 里那个"`static` 编码表"隐患的根源。

## 六、一句话记住哈夫曼树

> **哈夫曼树是"每次合并权值最小的两棵"建出来的带权路径最短二叉树：信息全在叶子、非叶子只有权值当骨架；根权值一定等于所有权值之和（实测 67），WPL 等于所有非叶子节点权值之和（实测 157）；`Node` 实现 `Comparable` 是为了让 `Collections.sort` 每轮把最小的顶到前面，但"每轮整体排序"是 O(n² log n)，正确做法是换成 `PriorityQueue` 做到 O(n log n)；同一组权值能建出形态不同、WPL 相同的多种树，所以压缩端和解压端必须共享同一张编码表。**

## 七、往下学什么

1. **`PriorityQueue<Node>` 重写一遍**：`offer` 全部、`while (pq.size() > 1)` 里 `poll` 两次 + `offer` 一次，代码更短、复杂度从 O(n² log n) 降到 O(n log n)。这是这篇代码最值得马上改的一处。
2. **哈夫曼编码**：树建好之后"左 0 右 1"就是变长前缀码，接 [哈夫曼编码.md](../huffmancode/%E5%93%88%E5%A4%AB%E6%9B%BC%E7%BC%96%E7%A0%81.md)。
3. **哈夫曼树是贪心算法的标准例子**：可以顺手证明"为什么每次取最小两个不会更差"（反证法：任何最优树里最小的两个一定在最深层且互为兄弟）。
4. **带约束的变体**：k 叉哈夫曼树（每次合并 k 个，不足要补 0 权值节点）、自适应哈夫曼（Forest / Vitter 算法，边读边建树，不用先扫一遍统计）。
5. **回到 JDK**：`PriorityQueue` 的底层就是[堆](../tree/%E5%A0%86%E6%8E%92%E5%BA%8F.md)，`Comparator` 减法比较的溢出坑在 `Arrays.sort` 的文档里被明确警告过。
