# 二叉排序树（BST：把"有序"做进结构里）

> 对应程序：[BinarySortTreeDemo.java](./BinarySortTreeDemo.java)
> 前置阅读：[二叉树.md](../tree/%E4%BA%8C%E5%8F%89%E6%A0%91.md)（同一棵树两种"删除"语义的对照）、[搜索算法.md](../search/%E6%90%9C%E7%B4%A2%E7%AE%97%E6%B3%95.md)（"二分的前提是有序，可代码一行都不检查"）
> 下文所有树形、中序序列、比较次数、耗时、异常都是本机（JDK 21）实跑的输出。标注"探针"的数字是把 `main` 换成测试代码后跑的，仓库里没有那个变体。
> 树形一律写成 `值(L左孩子,R右孩子)`，例如 `7(L3,R10)` 表示根是 7、左孩子 3、右孩子 10。

## 一、先看实测：不排序，中序遍历就是有序的

按 `7, 3, 10, 12, 5, 1, 9` 的顺序 `add`，最后再手动补一个 `2`，得到的树是：

```
        7
      /   \
     3     10
    / \   / \
   1   5 9   12
    \
     2
```

树形实测：`7(L3,R10) 3(L1,R5) 1(R2) 2() 5() 10(L9,R12) 9() 12()`。`main` 实际打印的四段中序遍历：

| 时机 | 实测输出 |
|---|---|
| 初始 | `1 2 3 5 7 9 10 12` |
| 删除叶子节点 5 后 | `1 2 3 7 9 10 12` |
| 删除只有一颗子树的节点 1 后 | `2 3 7 9 10 12` |
| 打印"删除有两颗子树的节点7后"之后 | `2 3 7 9 12` |

⚠️ 最后一段的**注释和代码对不上**：`System.out.println("删除有两颗子树的节点7后")` 下面一行是 `binarySortTree.delete(10)`，删的是 10。探针实测删 7 走的也是同一条分支（结果是 `1 2 3 5 9 10 12`），所以是打印文案错了，不是逻辑错了。

"中序遍历 = 有序"不是巧合，是这棵树**唯一的约束**（左 < 自己 ≤ 右）推出来的：中序正好是"左、自己、右"，把每条不等式按顺序念一遍就是升序。这也是[搜索算法.md](../search/%E6%90%9C%E7%B4%A2%E7%AE%97%E6%B3%95.md) 第十四节说的"查找和有序维护合成一件事"。

## 二、`add`：一个 `<` 把整棵树的规矩立起来了

```java
if (node.value < this.value) {
    if (this.left == null) this.left = node;
    else this.left.add(node);        // 继续往左下走
} else {
    if (this.right == null) this.right = node;
    else this.right.add(node);
}
```

三点值得注意：

1. **插入就是查找 + 挂一根指针**。走的路线和 `search` 一模一样，只是走到 `null` 时把新节点挂上，代价都是"树的高度"。
2. **相等的值走右边**（`else` 分支包含 `==`）。探针实测在 `7, 3, 10` 之后连插三个 5，树形是 `7(L3,R10) 3(R5) 5(R5) 5(R5) 5() 10()` —— 第一个 5 挂到 3 的右边，第二个 5 挂到第一个 5 的右边，整条相等值会拉成一条右链，中序是 `[3, 5, 5, 5, 7, 10]`，仍然有序。
3. **没有旋转、没有 rehash、没有任何"平衡"字样**。这三条里第 3 条是本篇后面所有麻烦的来源。

## 三、形状完全由插入顺序决定（实测代价）

同一批数 `1, 3, 5, …`，换个顺序插出来的树差很多（探针）：

| 数据量 | 顺序插入的高度 | 随机插入的高度 | 顺序插入查最大值比较次数 | 随机插入查最大值比较次数 |
|---|---|---|---|---|
| 100 | 100 | 15 | 100 | 4 |
| 1000 | 1000 | 22 | 1000 | 9 |
| 10000 | 10000 | 28 | 10000 | 8 |

顺序插入直接把树插成一条**右斜链表**（高度 = n），查找退化成[线性查找](../search/%E6%90%9C%E7%B4%A2%E7%AE%97%E6%B3%95.md)；随机插入的高度只有二三十。

2 万个数的更大一组（探针，`new Random(1994)` 打乱）：

| 插入顺序 | 建树耗时 | 高度 | 抽样 207 次查找的平均比较 |
|---|---|---|---|
| 升序 `0..19999` | 415ms | 20000 | 9992.0 |
| 随机打乱 | 1ms | 33 | 17.75 |

耗时那一栏也别忽略：**同样是插 2 万个节点，顺序插比乱序插慢 400 倍**，因为每次插入都要递归下沉两万层，光栈帧就是笔钱（第七节还有一栏更狠的）。

> 这就是"平均 `O(log n)`、最坏 `O(n)`"的真实含义：不是常数大一点，是**换成线性**了。要拿到最坏保证，就得引入旋转（AVL / 红黑树），也就是 JDK 的 `TreeMap`。

## 四、`delete` 的三种情况，指针到底怎么动

`delete` 分三步：`search` 找到目标 → 判断是叶子/单孩子/双孩子 → 找到 `parent` 后动指针。下面每行都是**把第一节那棵树重新插一遍，只删这一个值**（探针实测），这样六种情况可以互相对照：

| 删除 | 类型 | 删除后中序 | 删除后形状（片段） |
|---|---|---|---|
| `delete(5)` | 叶子 | `1 2 3 7 9 10 12` | `3(L1,)` —— 5 从 3 的右边摘掉 |
| `delete(9)` | 叶子 | `1 2 3 5 7 10 12` | `10(R12)` —— 9 从 10 的左边摘掉 |
| `delete(1)` | 只有一个右孩子 2 | `2 3 5 7 9 10 12` | `3(L2,R5)` —— 2 顶上来，**父节点直接跨过 1 挂 2** |
| `delete(3)` | 双孩子(1,5) | `1 2 5 7 9 10 12` | `7(L5,R10) 5(L1,)` |
| `delete(10)` | 双孩子(9,12) | `1 2 3 5 7 9 12` | `7(L3,R12) 12(L9,)` |
| `delete(7)`（根） | 双孩子(3,10) | `1 2 3 5 9 10 12` | `9(L3,R10) 10(R12)` |

关键在**双孩子这一支，改的是值不是形状**：

```java
int minVal = delRightTreeMin(targetNode.right); // 去右子树拿最小值，并把它原来那个节点删掉
targetNode.value = minVal;                     // 抄到被删节点的位置上
```

`delete(3)` 时拿右子树最小值 5 顶上来，于是 **3 这个位置变成 5**，而原来那个 5 的节点被摘掉，1 留在新的 5 下面。`delete(7)` 同理，根的值变成 9，而 9 原来站的 10 的左边空出来。

这里有个隐藏语义：**节点对象没换，换的是 `value`**。如果外面有代码之前拿着"根节点"的引用，它现在拿到的还是同一个对象，但值已经变了。真要按对象身份删除，得改成"把要删的节点和替补节点交换位置"，而不是抄值。

对照[二叉树.md](../tree/%E4%BA%8C%E5%8F%89%E6%A0%91.md) 里的 `deleteNode`：那个是"这是二叉树，删掉你就要断开一整棵子树"，随便挑一条规则（左孩子顶上）就行；这里是**二叉排序树**，删完之后必须仍然满足"左小右大"，所以才分成三种情况 + 值顶替。**同一套指针操作，因为多了一条不变式，难度完全不同。**

## 五、⚠️ 实测两个会当场炸的 bug

### 1）单孩子分支漏判 `parent.left == null` → `NullPointerException`

删除"只有一个右孩子"的节点时，代码是这么写的（`BinarySortTreeDemo.java:136`）：

```java
} else {                                  // targetNode 只有右孩子
    if (parent != null) {
        if (parent.left.value == targetNode.value) {   // ← parent.left 可能是 null
            parent.left = targetNode.right;
        } else if (parent.right.value == targetNode.value) {
            parent.right = targetNode.right;
        }
    } else root = targetNode.right;
}
```

叶子那一支用的是 `parent.left != null && parent.left.value == value`，**先把判空写全了**；这两支只判了 `parent != null`，没判 `parent.left != null`。于是只要 **targetNode 是父节点的右孩子、而父节点没有左孩子**，第一行判断就炸。探针实测：

| 插入 | 删除 | 结果 |
|---|---|---|
| `7, 10, 12`（右斜链） | `delete(10)` | `NullPointerException @ BinarySortTreeDemo.java:136` |
| `7, 10, 12, 15` | `delete(12)` | 同上（136 行） |
| `10, 15, 12` | `delete(15)` | `NullPointerException @ BinarySortTreeDemo.java:128` |
| `5, 5`（相等的值挂右边） | `delete(5)` | 同上（136 行） |
| `5, 5, 8` | `delete(5)` | 同上（136 行） |
| `10, 7, 3`（左斜链） | `delete(7)` | 成功，中序 `3 10` |

**左斜链没事、右斜链炸**，典型的"判空只写了一半"。注意第 3 行那个例子（`10, 15, 12` 删 15）炸在 **128 行**：那一支是"target 只有左孩子"，同样先解了 `parent.left`，所以**两条单孩子分支都漏判**，只是 136 那条更容易碰到。而且这个 bug 和 `add` 里"相等值走右边"是配套的：只要有一段连续递增的数据，右斜链就必然出现。

### 2）`delete` ↔ `delRightTreeMin` 无限互递归 → `StackOverflowError`

最小复现只要三个数：插 `5, 3, 5`（右孩子和根相等），然后 `delete(5)`。链路：

1. `search(5)` 从根开始，第一个就等于 5 → `targetNode` 是**根**；
2. 根有左右孩子 → 走双孩子分支 → `delRightTreeMin(根的右孩子)`；
3. 右子树的最小节点就是那个值为 5 的右孩子本身（它没有左孩子）→ 于是 `delete(target.value)`，也就是 `delete(5)`；
4. **回到第 1 步**，`search(5)` 又找到根，根还是两个孩子……

`delete → delRightTreeMin → delete → …` 无限套娃直到爆栈。探针抓到的栈就是这样来回刷的两帧。根因是 `delRightTreeMin` 用**按值**的 `delete(value)` 删最小节点，而值在这棵树里不唯一 —— 拿"值"当身份，就会在重复值上把自己再删一遍。

修法两种：① `delRightTreeMin` 别调公共的 `delete`，直接改指针（记住最小节点的父亲，或者给节点加 `parent` 字段）；② `add` 里 `<` 改成 `<=` 走左边、或给节点加个 `count` 字段只存一份值。

### 3）20000 组随机差分测试：炸是响的，但炸得不少

探针做法：随机建一棵 3~12 个节点的树（值从 0~29 里随机取，所以**必然会出现重复值**），记下一个"参照表"（同一个多重集排好序），删掉一个随机值，然后把中序遍历和参照表逐个比对：

```
20000 组随机建树+删一个随机值：正确 16225  NPE 1597  栈溢出 2178  结果错 0
```

也就是说 **18.9% 的删除操作当场炸**（8.0% NPE + 10.9% 爆栈），但**没有一次给出错误结果** —— 炸的时候异常会告诉你。这一点和[搜索算法.md](../search/%E6%90%9C%E7%B4%A2%E7%AE%97%E6%B3%95.md) 里"二分查找在无序数组上错了也不吭声"正好是两类 bug：这里宁可炸也不静默答错。栈溢出那个样例（插 `29, 28, 18, 27, 29, 5, 12, 18` 后 `delete(29)`）探针还对比了炸前炸后的树：**父子指针一字未改、8 个节点、无环** —— 也就是说这次删除什么都没做成，但也没把树弄坏。

## 六、静默行为：三种"什么都没发生"

探针实测，这些情况**都不报错**：

| 场景 | 实测 |
|---|---|
| `delete(4)`，树里没有 4 | `search` 返回 null → 直接 `return`，中序一个数都没变 |
| 空树上 `delete(1)` | `root == null` → `return`，无异常 |
| 只剩根节点时 `delete(根)` | 命中 `root.left == null && root.right == null` → `root = null`，树变空 |
| `searchParent(根的值)` | 返回 **null**（根没有父亲）—— 所以删除分支里必须判 `parent != null`，他代码里那句"防止空指针异常，删到最后两三个节点时"就是为这个加的 |
| `searchParent(不存在的值)` | 也返回 null |

`delete` 是 `void`、找不到也不吭声，所以**"我删了吗"和"删掉了吗"在这份代码里问不出区别**。真实库里要么返回 `boolean`，要么抛异常。

## 七、递归本身也会爆栈（对照 递归.md 的两条红线）

探针用升序数据插成一条链，然后看哪个方法先撑不住（命令行 `java` 默认栈，`-Xss` 没设）：

| 升序插入个数 | 实测 |
|---|---|
| 1000 | `add` / `infixOrder` / `search` 全部正常 |
| 5000 | **`add` 能插完，`infixOrder` 先 `StackOverflowError`** |
| 20000 | 同上，`infixOrder` 处爆 |
| 50000 | 连 `add` 都爆 |

`add` 每层只做一次比较、一次赋值，`infixOrder` 每层还要走 `System.out.println(this)` → `toString`，栈帧更大，所以**它比 `add` 更早炸**（5000 个时 `add` 能插完、遍历先爆）。结论和[递归.md](../recursion/%E9%80%92%E5%BD%92.md) 一致：递归算法的上限不是数据量，是**栈深度**；而树形递归的深度由数据顺序决定 —— 这两件事叠在一起，顺序输入的 BST 就是最坏情况。想彻底躲开，得把遍历改成显式栈（`Deque`）版本。

## 九、一句话记住二叉排序树

> **二叉排序树 = 用"左小右大"这一条不变式把查找、插入、删除都变成"从根往下走一条路径"，所以中序遍历天生有序（实测 `1 2 3 5 7 9 10 12`）、代价是树高；没有旋转就没有平衡：顺序插入直接退化成链表，实测 1 万个数据顺序插高度 10000、查最大值要比较 10000 次，随机插高度 28、只比 8 次；删除的三种情况里双孩子是"拿右子树最小值抄过来再删掉它"，改的是值不是节点身份；这份实现实测有两个会当场炸的 bug —— 单孩子分支漏判 `parent.left` 导致右斜链一删就 `NullPointerException`，`delRightTreeMin` 按值调 `delete` 遇到重复值就和 `delete` 无限互递归爆栈，20000 组随机测试 18.9% 的删除炸掉、但 0 次给出错答案；所有"找不到"的情况都是静默 `return`，`searchParent(根)` 返回 null 是唯一要单独处理的父亲。**

## 十、往下学什么

1. ** AVL / 红黑树**：只差"插完/删完做一次旋转重排"这一步，就有了最坏 `O(log n)`。Java 标准库的 `TreeMap`/`TreeSet` 就是红黑树，读懂本篇再去看它的 `put`，会发现结构完全一样、多的只是旋转和颜色。
2. **`delRightTreeMin` 换成迭代 + 直接改指针**：顺手把第五节的两个 bug 一起修掉（不再按值删、不再依赖 `parent.left` 的猜测），并让删除返回 `boolean`。
3. **给节点加 `parent` 指针**：删除时就不用先 `searchParent` 再猜左右侧了，`ThreadedBinaryTree`（[线索二叉树.md](../tree/%E7%BA%BF%E7%B4%A2%E4%BA%8C%E5%8F%89%E6%A0%91.md)）解决的是同一类"我找不到我爹"的问题，两种思路值得对照。
4. **重复值单独处理**：要么节点里加 `count`（值只存一份），要么固定"相等往左"，本篇实测过：`add` 把相等值全塞右边，等于给删除埋了个雷。
5. **顺序统计量**：在每个节点存"以我为根的子树大小"，就能 `O(log n)` 回答"第 k 小"和"排名是多少" —— 这是有序数组和[哈希表](../hashtable/%E5%93%88%E5%B8%8C%E8%A1%A8.md)都做不到的（哈希表放弃了顺序，有序数组放弃了便宜的插入）。
6. **显式栈改写遍历**：第七节那次爆栈说明递归版的健壮性依赖输入顺序，面试和工程里都会要求写出 `while + Deque` 的版本。
