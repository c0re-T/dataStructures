# 哈夫曼编码（变长前缀码压缩与解压）

> 对应程序：[HuffmanCode.java](./HuffmanCode.java)
> 前置阅读：[哈夫曼树.md](../huffmantree/%E5%93%88%E5%A4%AB%E6%9B%BC%E6%A0%91.md) —— 那篇管建树，这篇管"把树变成一张编码表，然后真的压一次、再真的解回来"。
> 下文所有字节数组、编码表、位数都是本机（JDK 21）实跑 `main` 的输出；标注"探针副本"的那条是把 `main` 里的字符串换掉后跑的，仓库里没有那个变体。

---

## 一、先看实测结果

输入 `String content = "i like like like java do you like a java";`

| 阶段 | 实测 |
|---|---|
| 原始 | 40 个字节（`bytes.length = 40`，即 320 位） |
| 统计出的编码表 | 12 条（下面第三节） |
| 编码后的二进制串 | **133 位** |
| 打包成 `byte[]` | **17 个字节**（`[-88, -65, -56, ..., -90, 28]`） |
| 解压结果 | `i like like like java do you like a java` ✅ 与原文逐字一致 |

`40 → 17`，压缩到 **42.5%**（按位算是 133/320 = 41.6%）。`133 位 → 17 字节` 也对得上：`(133 + 7) / 8 = 17`。

---

## 二、为什么变长编码能解得开

定长编码（ASCII 每字符 8 位）浪费在"出现次数少的字符也占 8 位"。变长编码想省，就必须解决**前缀歧义**：

```
   假设 a=0, b=01, c=10     收到 "010" → 是 a|b? 不，是 a+b 还是 b+c 还是 a+a+c？  解不出来
```

**前缀编码**：任何一个字符的编码都不是另一个字符编码的前缀 → 收到就能唯一切开。哈夫曼编码天然满足，因为**所有字符都只放在叶子上**（[哈夫曼树.md](../huffmantree/%E5%93%88%E5%A4%AB%E6%9B%BC%E6%A0%91.md) 第三节第 1 点），从根走到某个叶子的路径，绝不会是走到另一个叶子路径的前缀。

约定：**左分支记 0，右分支记 1**，走到叶子时攒下的那串 0/1 就是这个字符的编码。

## 三、五个步骤，对应五个方法

```java
byte[] bytes = content.getBytes();
byte[] huffmanBytes = huffmanZip(bytes);          // 压缩（一把梭）
byte[] decode = decode(huffmanBytes, huffmanCodes);   // 解压
```

`huffmanZip` 就是把前三步套起来：

```java
private static byte[] huffmanZip(byte[] bytes) {
    return zip(bytes, getCodes(createHuffmanTree(getNodes(bytes))));
}
```

| 方法 | 干什么 | 实测产物 |
|---|---|---|
| `getNodes(byte[])` | `HashMap` 统计每个字节出现次数 → 每个键值对变成一个 `Node(data, weight)` | 12 个节点 |
| `createHuffmanTree(List<Node>)` | 每轮 `Collections.sort` 后取最小两个合并（和上一篇同一套贪心） | 根权值 = 40 |
| `getCodes(node, code, sb)` | 递归走树，左传 `"0"` 右传 `"1"`，**只在 `node.data != null`（叶子）时把路径存进表** | 12 条编码表 |
| `zip(bytes, codes)` | 按原字节顺序把编码拼成一长串 0/1，再每 8 位 `Integer.parseInt(str, 2)` 打成一个 byte | 17 字节 |
| `decode(bytes, codes)` | 把 byte 还原成 0/1 串 → 编码表**反转成 `Map<String,Byte>`** → 从 i 开始试 `count=1,2,3…` 直到在表里命中 | 原 `byte[]` |

实测编码表（`key` 是字节值，`value` 是编码）：

```
{000=108, 01=32, 100=97, 101=105, 11010=121, 0011=111,
 1111=107, 11001=117, 1110=101, 11000=100, 11011=118, 0010=106}
```

翻成人话：`32` 是空格（出现 9 次，最频繁）→ 只给 2 位 `01`；`121` 是 `y`（只出现 1 次）→ 给了 5 位 `11010`。**权值越大路径越短**，这就是省地方的全部来源。

## 四、两个只有写起来才知道的细节

### 1）`getBinaryString` 里那句 `temp |= 256`

```java
int temp = b;                      // byte 会自动符号扩展成 int：-88 → 0xFFFFFFA8
if (needFullEight) temp |= 256;    // 强行把第 9 位置 1 → 1 0000 0000 | ...
String str = Integer.toBinaryString(temp);
if (needFullEight) return str.substring(str.length() - 8);   // 取后 8 位
```

问题在于 `Integer.toBinaryString(负数)` 会给你 **32 位**，直接截 8 位又麻烦又容易错。`|= 256` 是把第 9 位（值 256）置 1，这样 `toBinaryString` 至少返回 9 位、且低 8 位就是我们要的，`substring(length-8)` 一刀就干净。这是"补高位"最省事的写法。

### 2）最后一个字节**故意不补满 8 位**

```java
boolean isLastByte = (i == huffmanBytes.length - 1);
stringBuilder.append(getBinaryString(!isLastByte, huffmanByte));   // 最后一个 → false
```

因为 133 位打包成 17 字节时，最后一个字节只装了 5 位有效数据、低位是空的。如果按 8 位补满还原，就会多出 3 个假 0，解码时要么匹配错、要么越界。所以最后一个字节直接取 `Integer.toBinaryString` 的自然长度。

⚠️ **这一步只在"最后一组恰好以 1 开头"时才对**，实测本例最后一个字节是 `28` → `11100`，首位是 1，自然长度 5 位正好等于打包时的有效位数，所以侥幸对上。反例实测：把 `content` 换成 `"ab"`，两个字符各 1 次 → 编码是 `a=0`、`b=1` → 拼出 `01` → 打包成 1 个字节 `[1]`；解压时 `Integer.toBinaryString(1)` 只给 `"1"`，**开头那个 0 被吃掉了**，于是解出来是：

```
压缩后的huffmanBytes = [1] 长度：1
解码后的字符串 = b          ← 原串是 "ab"，a 无声消失
```

**"最后一组以 0 开头"就丢位，而且不报任何错。** 真实压缩格式必须把"最后一个字节有几位有效"（或原始总位数）一起存下来，这是这份代码离"能用的压缩器"差的关键一步。

## 五、⚠️ 实测：整串只有一个字符时，会静默丢数据

把 `main` 里的 `content` 换成 `"aaaa"`（探针副本，仓库里没有这个变体）跑：

```
压缩后的huffmanBytes = [] 长度：0
反向查询map={=97}
解码后的字符数组 = []
解码后的字符串 =
```

4 个字符压成 **0 字节**，解压回来是**空串** —— 没有异常、没有提示，数据就这么没了。链路是这样断的：

1. `getNodes` 只统计出 1 个节点 `{a:4}`；
2. `createHuffmanTree` 的 `while (nodes.size() > 1)` 一次都不进，直接返回那个**叶子本身**当根；
3. `getCodes` 一上来就命中"是叶子"分支，把 `sb2`（此时是空串）当编码存进表 → 表变成 `{"a": ""}`；
4. `zip` 拼出来的 0/1 串长度为 0 → `len = 0` → 返回空数组；
5. `decode` 对空串的双重循环一次都不进，返回空数组。

**根因是哈夫曼树至少需要两个叶子才有意义**（一个字符不需要编码，直接记长度就行）。修法：`huffmanZip` 前判一下 `nodes.size() < 2`，这种情况直接原样存 + 打个"未压缩"标记。另外别忘了第四节那个 `"ab"` —— 两种字符能建出树，但依然会因"最后一组以 0 开头"丢字符，所以这个程序要修的其实是两处。

## 六、⚠️ 编码表是 `static` 的，这是隐患不是便利

```java
static Map<Byte, String> huffmanCodes = new HashMap<>();
static StringBuilder sb = new StringBuilder();
```

`main` 里 `decode(huffmanBytes, huffmanCodes)` 能拿到表，**纯粹是因为前一行 `huffmanZip` 顺手把这个静态字段填上了**。三个后果：

1. **换进程/换文件就解不开**：解压时必须重建同一张表，真实做法是把编码表序列化后**放在压缩数据前面一起存**。
2. **同一个进程里压第二段会被污染**：`huffmanCodes` 从不清空，第二次 `getCodes` 是往同一张表里 `put`，两次的结果会叠在一起；`sb` 同理。
3. **不可重入**：多线程同时压缩会互相写脏这张表。

顺带一句和上一篇呼应的：编码表本身依赖 `HashMap` 的遍历顺序和并列权值的先后（[哈夫曼树.md](../huffmantree/%E5%93%88%E5%A4%AB%E6%9B%BC%E6%A0%91.md) 第四节），所以**"压缩端算出来的表"是唯一可信来源**，绝不能解压端凭权值自己再推一遍。

## 七、动手验证剧本

```powershell
javac -encoding UTF-8 -d out src\com\ittxf\huffmancode\HuffmanCode.java
java -cp out com.ittxf.huffmancode.HuffmanCode
```

| 实验 | 怎么改 | 会看到什么 | 印证哪一节 |
|---|---|---|---|
| 1 | 把 `main` 里那一大段注释放开（拆解版） | 逐步骤打出 `nodes`、树、前序、编码表、压缩结果，和第三节的表一一对上 | 三节 |
| 2 | `content` 改成 `"aaaaaaaa"`（仍只有一种字符） | 和 `"aaaa"` 一样：压缩后长度 0、解压成空串 | 五节 |
| 3 | `content` 改成 `"ab"` | 压缩后 `[1]` 长度 1，解压只剩 `b` —— 前导 0 被吃掉 | 四节 2） |
| 4 | `content` 改成 `"i like java"`（11 字节） | 压缩后 5 字节、能正常解回；串越短、字符分布越平，省得越少 | 一节 |
| 5 | 在 `huffmanZip` 之后**再调一次** `huffmanZip` 压另一串文本，然后 `decode` | 编码表被两次结果污染，解压出来的字符串不对 | 六节 |
| 6 | 把 `decode` 里 `getBinaryString(!isLastByte, ...)` 改成恒传 `true` | 最后字节多补出 0，末尾解出乱码/越界 | 四节 2） |

第 3、5 条建议一定跑：一个是"不报错但数据没了"，一个是"表必须跟着数据走"，都是压缩类程序最真实的两类事故。

## 八、一句话记住哈夫曼编码

> **哈夫曼编码 = 把"出现次数"当权值建哈夫曼树，左 0 右 1，叶子到根的路径就是变长前缀码，所以权值大的字符编码短（实测空格 9 次只占 2 位、`y` 1 次要 5 位）；压缩是"统计 → 建树 → 生成表 → 按位拼接每 8 位打成一个 byte"（实测 40 字节 → 133 位 → 17 字节），解压是把表反转成 `编码→字节` 再从左往右试长度命中；两个字节级的技巧是 `temp \|= 256` 补高位、最后一个字节故意不补满 8 位（本例恰好首位是 1 才对，真实格式必须记录有效位数）；两个必须记住的坑是"整串只有一个字符会静默压成 0 字节"和"`huffmanCodes` 是 static 且从不清空，所以编码表必须随数据一起存、不能重复调用"。**

## 九、往下学什么

1. **把编码表序列化**：先写表（或写"字符 + 频次"）再写数据，才是能存文件的格式；顺手把 `static` 表改成方法内的局部变量传参，第六节三个问题一起消失。
2. **补上"最后一个字节有效位数"**：在文件头记一个 int，或者干脆记原始总位数，第四节那个"碰巧对"就变成"必然对"。
3. **对照 `Deflater`/GZIP**：JDK 自带的 `java.util.zip.DeflaterOutputStream` 是 LZ77 + 哈夫曼（DEFLATE），本篇是纯哈夫曼 —— 拿同一串文本量一下压缩率，就能明白"字典"比"变长编码"贡献大得多。
4. **算术编码 / ANS**：同样按概率压缩，但能突破"一个字符至少 1 位"的限制，接近信息熵下界。
5. **优先队列重写建树**：`PriorityQueue<Node>` 把 [哈夫曼树.md](../huffmantree/%E5%93%88%E5%A4%AB%E6%9B%BC%E6%A0%91.md) 第三节的 O(n² log n) 降到 O(n log n)，底层就是[堆](../tree/%E5%A0%86%E6%8E%92%E5%BA%8F.md)。
