# 哈夫曼编码（变长前缀码压缩与解压）

> 对应程序：[HuffmanCode.java](./HuffmanCode.java)
> 前置阅读：[哈夫曼树.md](../huffmantree/%E5%93%88%E5%A4%AB%E6%9B%BC%E6%A0%91.md) —— 那篇管建树，这篇管"把树变成一张编码表，然后真的压一次、再真的解回来"。
> 第七、八节是文件级实测：`main` 现在默认只跑 `unZipFile`，所以标"探针"的数字是把 `main` 换成测试代码（或用包级可见的 `huffmanCodes` / `zipFile` / `unZipFile` / `decode` / `getBinaryString` 直接调）后跑的，仓库里没有那些变体。所有数字来自本机 JDK 21。

---

## 一、先看实测结果

输入 `String content = "i like like like java do you like a java";`

| 阶段 | 实测 |
|---|---|
| 原始 | 40 个字节（`bytes.length = 40`，即 320 位） |
| 统计出的编码表 | 12 条（下面第三节） |
| 编码后的二进制串 | **133 位** |
| 打包成 `byte[]` | **17 个字节**（`[-88, -65, -56, ..., -90, 28]`） |
| 解压结果 | `i like like like java do you like a java` ✅ 与原文逐字一致 |

`40 → 17`，压缩到 **42.5%**（按位算是 133/320 = 41.6%）。`133 位 → 17 字节` 也对得上：`(133 + 7) / 8 = 17`。

---

## 二、为什么变长编码能解得开

定长编码（ASCII 每字符 8 位）浪费在"出现次数少的字符也占 8 位"。变长编码想省，就必须解决**前缀歧义**：

```
   假设 a=0, b=01, c=10     收到 "010" → 是 a|b? 不，是 a+b 还是 b+c 还是 a+a+c？  解不出来
```

**前缀编码**：任何一个字符的编码都不是另一个字符编码的前缀 → 收到就能唯一切开。哈夫曼编码天然满足，因为**所有字符都只放在叶子上**（[哈夫曼树.md](../huffmantree/%E5%93%88%E5%A4%AB%E6%9B%BC%E6%A0%91.md) 第三节第 1 点），从根走到某个叶子的路径，绝不会是走到另一个叶子路径的前缀。

约定：**左分支记 0，右分支记 1**，走到叶子时攒下的那串 0/1 就是这个字符的编码。

## 三、五个步骤，对应五个方法

```java
byte[] bytes = content.getBytes();
byte[] huffmanBytes = huffmanZip(bytes);          // 压缩（一把梭）
byte[] decode = decode(huffmanBytes, huffmanCodes);   // 解压
```

`huffmanZip` 就是把前三步套起来：

```java
private static byte[] huffmanZip(byte[] bytes) {
    return zip(bytes, getCodes(createHuffmanTree(getNodes(bytes))));
}
```

| 方法 | 干什么 | 实测产物 |
|---|---|---|
| `getNodes(byte[])` | `HashMap` 统计每个字节出现次数 → 每个键值对变成一个 `Node(data, weight)` | 12 个节点 |
| `createHuffmanTree(List<Node>)` | 每轮 `Collections.sort` 后取最小两个合并（和上一篇同一套贪心） | 根权值 = 40 |
| `getCodes(node, code, sb)` | 递归走树，左传 `"0"` 右传 `"1"`，**只在 `node.data != null`（叶子）时把路径存进表** | 12 条编码表 |
| `zip(bytes, codes)` | 按原字节顺序把编码拼成一长串 0/1，再每 8 位 `Integer.parseInt(str, 2)` 打成一个 byte | 17 字节 |
| `decode(bytes, codes)` | 把 byte 还原成 0/1 串 → 编码表**反转成 `Map<String,Byte>`** → 从 i 开始试 `count=1,2,3…` 直到在表里命中 | 原 `byte[]` |

实测编码表（`key` 是字节值，`value` 是编码）：

```
{000=108, 01=32, 100=97, 101=105, 11010=121, 0011=111,
 1111=107, 11001=117, 1110=101, 11000=100, 11011=118, 0010=106}
```

翻成人话：`32` 是空格（出现 9 次，最频繁）→ 只给 2 位 `01`；`121` 是 `y`（只出现 1 次）→ 给了 5 位 `11010`。**权值越大路径越短**，这就是省地方的全部来源。

## 四、两个只有写起来才知道的细节

### 1）`getBinaryString` 里那句 `temp |= 256`

```java
int temp = b;                      // byte 会自动符号扩展成 int：-88 → 0xFFFFFFA8
if (needFullEight) temp |= 256;    // 强行把第 9 位置 1 → 1 0000 0000 | ...
String str = Integer.toBinaryString(temp);
if (needFullEight) return str.substring(str.length() - 8);   // 取后 8 位
```

问题在于 `Integer.toBinaryString(负数)` 会给你 **32 位**，直接截 8 位又麻烦又容易错。`|= 256` 是把第 9 位（值 256）置 1，这样 `toBinaryString` 至少返回 9 位、且低 8 位就是我们要的，`substring(length-8)` 一刀就干净。这是"补高位"最省事的写法。

### 2）最后一个字节**故意不补满 8 位**

```java
boolean isLastByte = (i == huffmanBytes.length - 1);
stringBuilder.append(getBinaryString(!isLastByte, huffmanByte));   // 最后一个 → false
```

因为 133 位打包成 17 字节时，最后一个字节只装了 5 位有效数据、低位是空的。如果按 8 位补满还原，就会多出 3 个假 0，解码时要么匹配错、要么越界。所以最后一个字节直接取 `Integer.toBinaryString` 的自然长度。

⚠️ **这一步只在"最后一组恰好以 1 开头"时才对**，实测本例最后一个字节是 `28` → `11100`，首位是 1，自然长度 5 位正好等于打包时的有效位数，所以侥幸对上。反例实测：把 `content` 换成 `"ab"`，两个字符各 1 次 → 编码是 `a=0`、`b=1` → 拼出 `01` → 打包成 1 个字节 `[1]`；解压时 `Integer.toBinaryString(1)` 只给 `"1"`，**开头那个 0 被吃掉了**，于是解出来是：

```
压缩后的huffmanBytes = [1] 长度：1
解码后的字符串 = b          ← 原串是 "ab"，a 无声消失
```

**"最后一组以 0 开头"就丢位，而且不报任何错。** 真实压缩格式必须把"最后一个字节有几位有效"（或原始总位数）一起存下来，这是这份代码离"能用的压缩器"差的关键一步。第八节第 1 条把这个坑量化了：**四种末段情况里只有一种全对，随机短文本总失败率实测 48%。**

## 五、⚠️ 实测：整串只有一个字符时，会静默丢数据

把 `main` 里的 `content` 换成 `"aaaa"`（探针副本，仓库里没有这个变体）跑：

```
压缩后的huffmanBytes = [] 长度：0
反向查询map={=97}
解码后的字符数组 = []
解码后的字符串 =
```

4 个字符压成 **0 字节**，解压回来是**空串** —— 没有异常、没有提示，数据就这么没了。链路是这样断的：

1. `getNodes` 只统计出 1 个节点 `{a:4}`；
2. `createHuffmanTree` 的 `while (nodes.size() > 1)` 一次都不进，直接返回那个**叶子本身**当根；
3. `getCodes` 一上来就命中"是叶子"分支，把 `sb2`（此时是空串）当编码存进表 → 表变成 `{"a": ""}`；
4. `zip` 拼出来的 0/1 串长度为 0 → `len = 0` → 返回空数组；
5. `decode` 对空串的双重循环一次都不进，返回空数组。

**根因是哈夫曼树至少需要两个叶子才有意义**（一个字符不需要编码，直接记长度就行）。修法：`huffmanZip` 前判一下 `nodes.size() < 2`，这种情况直接原样存 + 打个"未压缩"标记。另外别忘了第四节那个 `"ab"` —— 两种字符能建出树，但依然会因"最后一组以 0 开头"丢字符，所以这个程序要修的其实是两处。**同一个坑在文件上更狠：第八节第 2 条实测 10000 字节的同字符文件会压成 179 字节的"合法包"，解压完是 0 字节，而且两句"成功"都照常打印。**

## 六、⚠️ 编码表是 `static` 的，这是隐患不是便利

```java
static Map<Byte, String> huffmanCodes = new HashMap<>();
static StringBuilder sb = new StringBuilder();
```

`main` 里 `decode(huffmanBytes, huffmanCodes)` 能拿到表，**纯粹是因为前一行 `huffmanZip` 顺手把这个静态字段填上了**。三个后果：

1. **换进程/换文件就解不开**：解压时必须重建同一张表，真实做法是把编码表序列化后**放在压缩数据前面一起存**。第七节的 `zipFile` 就是照这个做法补上的，实测能跨进程解压。
2. **同一个进程里压第二段会被污染**：`huffmanCodes` 从不清空，第二次 `getCodes` 是往同一张表里 `put`，两次的结果会叠在一起；`sb` 同理。**实测这个污染不是"多占点地方"那么简单，是真的会把内容解错**，见第八节第 4 条。
3. **不可重入**：多线程同时压缩会互相写脏这张表。

顺带一句和上一篇呼应的：编码表本身依赖 `HashMap` 的遍历顺序和并列权值的先后（[哈夫曼树.md](../huffmantree/%E5%93%88%E5%A4%AB%E6%9B%BC%E6%A0%91.md) 第四节），所以**"压缩端算出来的表"是唯一可信来源**，绝不能解压端凭权值自己再推一遍。

## 七、文件压缩与解压：`zipFile` / `unZipFile`

第四节第 1 条和第六节说的"编码表必须跟着数据一起存"，`zipFile` 就是照着补的：

```java
try (
    FileInputStream  fis = new FileInputStream(srcFile);
    FileOutputStream fos = new FileOutputStream(dstFile);
    ObjectOutputStream oos = new ObjectOutputStream(fos);   // 对象流：能直接 writeObject(Map)
) {
    byte[] b = new byte[fis.available()];                   // 整个文件一次读进内存
    fis.read(b);
    byte[] huffmanBytes = huffmanZip(b);                    // 顺手把静态 huffmanCodes 填好
    oos.writeObject(huffmanBytes);                          // ① 先写压缩后的字节数组
    oos.writeObject(huffmanCodes);                          // ② 再写编码表本身
}
```

解压按**同样的顺序**读回来，顺序错了就 `ClassCastException`：

```java
byte[] huffmanBytes = (byte[]) ois.readObject();
Map<Byte, String> huffmanCodes = (Map<Byte, String>) ois.readObject();
byte[] bytes = decode(huffmanBytes, huffmanCodes);
fos.write(bytes);
```

三个细节值得记：读的是 `byte[]` 却要用 `ObjectOutputStream`，因为 `Map` 不是字节流能直接写的东西；`FileOutputStream` 一被创建，**目标文件就已经落盘了**（哪怕后面解压失败，第八节第 3 条就是这个后果）；`fis.available()` 只对本地文件可靠，网络流不能这么用。

### 实测：四种文件的压缩比

四个样本各压一遍（探针，`in.png` 就是 `main` 注释里那张 `filePath/pg.png`）：

| 样本 | 原字节 | 压缩字节 | 码表序列化后 | zip 总字节 | 相对原文件 | 解压结果 |
|---|---|---|---|---|---|---|
| `corpus.txt`（仓库 35 个 `.java` 拼起来） | 197,390 | 137,760 | 3,335（167 条） | 141,118 | **71.5%** | 抛 `StringIndexOutOfBoundsException`（末段 7 位、首位 0） |
| `in.png` | 1,270,114 | 1,146,399 | 4,984（256 条） | 1,151,406 | **90.7%** | 字节完全一致 |
| `made.zip`（已经是 zip） | 41,154 | 41,154 | 4,754（256 条） | 45,931 | **111.6%** | 不一致，多出 3 字节 |
| `rand.bin`（1 MiB 随机字节） | 1,048,576 | 1,048,576 | 4,754（256 条） | 1,053,353 | **100.5%** | 不一致，多出 3 字节 |

读这张表要点：

- **文本能省 28.5%，图片只省 9.3%**。PNG 内部已经做过熵编码，字节分布接近均匀，256 种值全用到 → 每个字符的编码都要 8 位，**哈夫曼一点便宜都没占到**（`压缩字节` 一栏和原文件一模一样），反倒贴一张 4,754 字节的码表，所以 zip 反而更大。随机字节同理。
- 23 字节是对象流的固定开销：四行的 `压缩字节 + 码表` 都比 `zip 总字节` 少 23（流头 + 两个对象头）。
- `in.png` 这次能成功是**运气**：末段正好 3 位且首位是 1，第八节第 1 条讲的就是这件事。他 `main` 注释里那次跑出来的 `filePath/pg.png.huffman.zip` 是 1,151,406 字节，和探针这一行完全对上；`cmp filePath/pg.png filePath/pg.unzip.png` 也没有输出 —— 这次往返确实逐字节一致。

### 实测：码表是小文件的绝对主导成本

| 正文 | 原字节 | zip 字节 | 其中码表 |
|---|---|---|---|
| `"a"` | 1 | 179 | 156 |
| `"ab"` | 2 | 192 | 168 |
| 第一节那句 40 字节 | 40 | 353 | 313 |

第一节"40 → 17"看着很漂亮，那是**只在内存里比 `byte[]` 的长度**。一旦真的要落盘，编码表必须一起存，40 字节的文件变成 353 字节，**膨胀 782%**。这就是为什么真实压缩格式都要分块（每个块重新统计一次码表，块太小码表亏、块太大自适应不了）。

### 实测：耗时与内存量级

`in.png`（1,270,114 字节）各跑 7 次取中位：`zipFile` **71ms**（7 次是 52~120），`unZipFile` **214ms**（7 次是 182~559）。解压比压缩慢三倍，原因在 `decode` 里那段 `while (flag)` 是从 `count = 1` 开始一个个试长度去 `HashMap` 里撞，等于每解一个字符平均要查一半的码长。

探针还量了编码后的比特串长度：**9,171,187 个字符**（对应 1,146,399 字节）。`StringBuilder` 存的是 `char`，一个 2 字节 → 光这一根字符串就约 17.5 MiB，是原文件的 14 倍。**这套实现全程把整个文件和整条比特串都放在内存里**，要压大文件得改成流式分块。

## 八、⚠️ 文件级的四个坑，全部实测过

### 1）最后一个字节"不补满 8 位"只在一种情况下是对的

`decode` 里对最后一个字节传的是 `getBinaryString(false, b)`，也就是直接拿 `Integer.toBinaryString` 的自然结果。探针实测各种字节值：

| byte | 真实二进制 | 补高位（对） | 不补高位（现在这么写） |
|---|---|---|---|
| `-127` | `10000001` | `10000001`（8 位） | `11111111111111111111111110000001`（**32 位**，多 24） |
| `-128` | `10000000` | `10000000` | 同上，32 位 |
| `1` | `00000001` | `00000001` | `1`（**1 位**，少 7） |
| `50` | `00110010` | `00110010` | `110010`（少 2） |
| `127` | `01111111` | `01111111` | `1111111`（少 1） |

于是打包出来的最后一个字节，还原时有四种局面。探针按末段位数和首位把随机样本分成四类，各取 200 个（**每一类都是重新构造、重新压缩的样本**）：

| 末段情况 | 200 个样本的解压结果 |
|---|---|
| 正好 8 位、首位 1（这个字节是负数） | 一致 **0**，内容不同 200 |
| 正好 8 位、首位 0 | 一致 **0**，内容不同 120，抛异常 80 |
| 不足 8 位、首位 1 | 一致 **200** ✅ |
| 不足 8 位、首位 0 | 一致 **26**，内容不同 106，抛异常 68 |

只有第三类是对的。合计下来：**随机短文本 300 组 → 完全一致 156、内容不同 88、抛 `StringIndexOutOfBoundsException` 56，失败率 48%**。而第七节 `made.zip` / `rand.bin` 那两行"多出 3 字节"就是第一类的账：负数被符号扩展成 32 位 → 凭空多出 24 个 `1`，而这两张表 256 种字符的编码几乎全是 8 位，24 ÷ 8 = 3 → 正好多解出 3 个字符。

`in.png` 为什么运气好？探针算出它编码后共 9,171,187 位，`9171187 % 8 = 3`，末段 3 位；最后一个压缩字节是 `6` → `toBinaryString` 给 `110`，正好 3 位，一位不多一位不少。**这是碰巧，不是设计。**

**修法**：文件头多存一个 `byte`，记"最后一个字节有几位有效"（或者直接存原始总位数），`decode` 时按它补零或截断。

### 2）只有一种字节值的文件：压得越狠，解出来越是空的

探针写一个 10,000 字节、全是 `'a'` 的文件：

```
zipFile：没报错，码表 = {97=}，包 179 字节（原 10000）
unZipFile：没报错，输出 0 字节
```

第五节在字符串上看到的"压成 0 字节"，落到文件上变成**一个 179 字节的合法 zip 包 + 一次完全成功的解压 + 一个 0 字节的输出文件**。179 字节全是被序列化的那张 `{"a": ""}` 码表。日志里两行"压缩成功！""解压成功！"都打了，数据一个都没回来。

同一个道理：**空文件**（0 字节）会在 `createHuffmanTree` 的 `nodes.get(0)` 上抛 `IndexOutOfBoundsException`（`getNodes` 返回空列表，`while (nodes.size() > 1)` 一次都不进），**1 字节文件**同样得到 `{120=}` 这张空编码码表、落盘 179 字节。

### 3）失败只打在控制台，方法照常返回

`zipFile` / `unZipFile` 的 `catch` 里只有 `e.printStackTrace()`，方法签名是 `void`。实测两个后果：

| 场景 | 实测 |
|---|---|
| 源文件不存在 | 抛 `FileNotFoundException`，但因为 `FileInputStream` 在 `FileOutputStream` **之前**创建，目标文件**没有**被创建 |
| 压缩包被截断成一半 | 抛 `EOFException`，而输出文件**已经被创建了，0 字节** |

所以调用方完全没法知道成功没有：`new File(dst).exists()` 在第一种情况是 false、第二种是 true，但返回值都是 `void`，日志还照打"压缩成功！"。真实做法要么让方法返回 `boolean`，要么让异常往外抛。

### 4）静态码表跨文件累积，会把内容解错

第六节第 2 条的实测版本。探针在同一个 JVM 里先压文件 A 再压文件 B（中间不 `clear`）：

| 实验 | 实测 |
|---|---|
| 压完 1 个文件、2 个、3 个… | 码表条目 2 → 5 → 6 → 6 → 6 条，**只增不减** |
| 先压全 `z` 的文件再压那句 40 字符 | 码表多出一条 `122=`（空串编码），包从 353 字节变 363 字节；因为脏条目是空串，反查表永远匹配不上，这次内容侥幸还是对的 |
| A、B 用**完全不相干的字符集**，各 200 组 | 结果仍正确 **29**，内容被解错 **171**（85.5%），抛异常 0 |
| 同样 200 组，但每次先 `clear` | 正确 108、错 92（剩下的错都是本节前三条的补位问题） |

第三行是重点：A 里那些字符的编码会原样留在表里，成为 B 的反查表里**合法但不属于 B 的编码**。解码是"从当前位开始试 `count=1,2,3…` 直到命中"，一条更短的脏编码只要恰好是 B 某段比特的开头，就会提前命中、吐出一个错字符，然后整条后续切分全歪。首个样本：B 是 `"sppsrqn"`（7 字节），解出来是 `"sascaccccccc"`（22 字节）。

**根因还是第六节那句：`huffmanCodes` 是 `static` 且从不清空。** 把它改成 `huffmanZip` 里的局部变量、当参数传下去，第 2、4 两条坑一起消失。

## 九、动手验证剧本

```powershell
javac -encoding UTF-8 -d out src\com\ittxf\huffmancode\HuffmanCode.java
```

| 实验 | 怎么改 | 会看到什么 | 印证哪一节 |
|---|---|---|---|
| 1 | 把 `main` 里那一大段注释放开（拆解版） | 逐步骤打出 `nodes`、树、前序、编码表、压缩结果，和第三节的表一一对上 | 三节 |
| 2 | `content` 改成 `"aaaaaaaa"`（仍只有一种字符） | 和 `"aaaa"` 一样：压缩后长度 0、解压成空串 | 五节 |
| 3 | `content` 改成 `"ab"` | 压缩后 `[1]` 长度 1，解压只剩 `b` —— 前导 0 被吃掉 | 四节 2） |
| 4 | `content` 改成 `"i like java"`（11 字节） | 压缩后 5 字节、能正常解回；串越短、字符分布越平，省得越少 | 一节 |
| 5 | 在 `huffmanZip` 之后**再调一次** `huffmanZip` 压另一串文本，然后 `decode` | 编码表被两次结果污染，解压出来的字符串不对 | 六节、八节 4） |

| 10 | 写一个全是同一个字符的文件（10000 个 `a`）压完再解 | 包 179 字节、两句"成功"都打印，输出文件 0 字节 | 八节 2） |

第 3、5 条建议一定跑：一个是"不报错但数据没了"，一个是"表必须跟着数据走"，都是压缩类程序最真实的两类事故。第七、八节的文件级实验（7~10）比字符串实验更有说服力，因为**文件会暴露固定成本**——码表、流头、末段补位这三件事在内存里都是看不见的。

## 十、一句话记住哈夫曼编码

> **哈夫曼编码 = 把"出现次数"当权值建哈夫曼树，左 0 右 1，叶子到根的路径就是变长前缀码，所以权值大的字符编码短（实测空格 9 次只占 2 位、`y` 1 次要 5 位）；压缩是"统计 → 建树 → 生成表 → 按位拼接每 8 位打成一个 byte"（实测 40 字节 → 133 位 → 17 字节），解压是把表反转成 `编码→字节` 再从左往右试长度命中；落盘时必须把编码表一起序列化（`zipFile` 实测固定多 23 字节 + 一张 3~5 KB 的码表，所以 40 字节的文件会变成 353 字节），文本实测压到 71.5%、已经是 zip/png 的数据压不动甚至反而变大（111.6%）；三个静默事故都来自"表"和"最后一个字节"：整串只有一种字符会静默压成空编码（实测 10000 字节的文件解压成 0 字节），最后那个字节不补高位只在"末段不足 8 位且首位是 1"时对（四类样本实测只有这一类 200/200 全对，随机短文本总失败率 48%），而 `huffmanCodes` 是 `static` 且从不清空，同进程连压两个字符集不同的文件实测 200 组里 171 组被解错。**

## 十一、往下学什么

1. **把 `static` 表改成局部变量传下去**：`huffmanZip` 返回一个"压缩结果 + 码表"的小对象，`zipFile` / `unZipFile` 用它，第八节第 2、4 两条坑当场消失，顺便解决不可重入的问题。
2. **补上"最后一个字节有效位数"**：在文件头记一个 `byte`（或干脆记原始总位数），第八节那张"四类只有一类对"的表就变成"四类全对"。这是这份代码离"能用的压缩器"最近的一步。
3. **改成流式分块**：现在整个文件 + 整条 `StringBuilder`（实测 1.27 MB 的图片要 9,171,187 个 char）都在内存里。DEFLATE/GZIP 是分块滚动统计码表的，块大小就是"码表固定成本"和"自适应能力"的折中，第七节那三行小文件实测就是这个折中的账单。
4. **对照 `Deflater`/`GZIP`**：JDK 自带的 `java.util.zip.DeflaterOutputStream` 是 LZ77 + 哈夫曼（DEFLATE），本篇是纯哈夫曼 —— 拿同一份 `corpus.txt` 量一下就能明白"字典"比"变长编码"贡献大得多（探针里 `made.zip` 那一行 41,154 字节压完还是 41,154 字节，正说明纯哈夫曼对已压缩数据一点办法没有）。
5. **算术编码 / ANS**：同样按概率压缩，但能突破"一个字符至少 1 位"的限制，接近信息熵下界；也顺带绕开"码表要不要跟着存"这个问题（用同一套概率模型即可）。
6. **优先队列重写建树**：`PriorityQueue<Node>` 把 [哈夫曼树.md](../huffmantree/%E5%93%88%E5%A4%AB%E6%9B%BC%E6%A0%91.md) 第三节的 O(n² log n) 降到 O(n log n)，底层就是[堆](../tree/%E5%A0%86%E6%8E%92%E5%BA%8F.md)；字符集 256 种时差别不大，但第八节那种"每次重新统计"的分块压缩里就会放大。
