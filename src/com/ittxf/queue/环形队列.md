# 环形队列（循环队列）

> 对应程序：[CircleArrayQueueDemo.java](./CircleArrayQueueDemo.java)
> 它是 [队列.md](./队列.md) 里那个「一次性数组队列」的**升级版**，专门治那个「数组还有空位却报满」的毛病。
> 建议先看队列.md 的第五节（假满），再看这份，前后就串起来了。

---

## 一、为什么要搞个"环形"

先把上一个版本的病复习一遍。一次性数组队列（`ArrayQueue`）里 `front`、`rear` 只会往右走、从不回头：

```
一次性队列（maxSize = 3）：

  取走 arr[0] 之后 →  front=0, rear=2

  ┌──────┬────┬────┐
  │(作废) │ 2  │ 3  │      addQueue(4) 判断 rear == maxSize-1 → 2 == 2 → "队列已满" ❗
  └──────┴────┴────┘      ↑ arr[0] 明明空着，可就是塞不进去，容量白白报废
        ↑
      front
```

**根因：指针不会回头。** 治法有两个方向：

| 方向 | 做法 | 代价 |
|---|---|---|
| 每次出队把所有数据整体左移 | 保持 `front` 永远在 0 | 出队变成 O(n)，白瞎了队列的 O(1) |
| **让指针绕圈走**（本程序选的） | 下标走到末尾就用 `% maxSize` 弹回 0 | 只要多写一个 `%`，代价是牺牲一个格子用来判满 |

所以"环形"不是真把数组弯成了圈，而是**用取余运算让下标在 `0 .. maxSize-1` 之间循环**，看起来像绕圈：

```
   普通数组：  0 → 1 → 2 → 3 →（没路了，撞墙）

   环形看待：  0 → 1
               ↑     ↓
               3 ← 2        下标 3 再往后一步回到 0，靠的就是 (3 + 1) % 4 = 0
```

## 二、改动清单：两个指针的语义被整体重定义了

这是本程序**最需要搞懂**的一节。它和上一版最大的区别不是多了个 `%`，而是 `front`、`rear` **各自指哪儿都换了**：

```java
// front 就指向队列的第一个元素，也就是说 arr[front] 就是队列的第一个元素，初始值 0
// rear 指向队列的最后一个元素的后一个位置。因为需要一个空位来区分是否满，初始值 0
this.front = 0;
this.rear = 0;
```

| | 一次性队列 `ArrayQueue` | 环形队列 `CircleArrayQueue` |
|---|---|---|
| `front` 初始值 | `-1` | `0` |
| `front` 指向 | 第一个元素的**前一格**（哨兵） | 第一个元素**本身** |
| `rear` 初始值 | `-1` | `0` |
| `rear` 指向 | 最后一个元素**本身** | 最后一个元素的**后一格**（下一个空位） |
| 取头元素 | `arr[front + 1]` | `arr[front]` |
| 写新元素 | `rear++; arr[rear] = n` | `arr[rear] = n; rear = ++rear % maxSize` |

大白话记两个新规矩：

- **`front` 就是"队首那个真货"** → 所以 `headQueue()` 直接 `return arr[front]`，不用再 `front + 1` 了。
- **`rear` 是"下一个该往哪儿放"** → 所以 `addQueue` 是**先赋值、后移动**（`arr[rear] = n;` 然后才 `rear = ++rear % maxSize;`），跟上一版的**先移动、后赋值**正好反了一次。

为什么要把 `rear` 改成"指向后一格"？因为这样 `rear` 天然就是"下一个可用槽"，配合取模绕圈最顺手；代价是**必须留一个空格子**当哨兵（第三节）。

> ⚠️ 这类"语义改动"最容易埋雷：如果只加了 `%` 却忘了同步改 `headQueue` 里的 `arr[front + 1]`，就会读出错位的数据。看代码时，**先确认 front/rear 的定义，再推导每个公式**，比背模板有用得多。

## 三、判满为什么要"牺牲一个格子"（面试必问）

```java
public boolean isEmpty() { return rear == front; }                    // 判空
public boolean isFull()  { return (rear + 1) % maxSize == front; }    // 判满：rear 再走一步就撞上 front
```

`rear == front` 就能判空了，那判满为什么不能用 `rear == front`？

```
假设允许把格子全塞满（maxSize = 4，塞 4 个）：

   front=0, rear=0（空）                    front=0, rear=0（塞满 4 个后绕回来）
   ┌───┬───┬───┬───┐                        ┌───┬───┬───┬───┐
   │   │   │   │   │                        │ 1 │ 2 │ 3 │ 4 │
   └───┴───┴───┴───┘                        └───┴───┴───┴───┘
    ↑─┘ 两指针都在 0                          ↑───┘ 绕一圈，两指针又都在 0

   两种状态 front == rear 完全一样 → 无法区分到底是空还是满 💥
```

所以必须**约定永远留一个格子不装数据**，让"满"变成"rear 再走一步就撞上 front"：

```
满状态（maxSize = 4，只能装 3 个，arr[3] 是被牺牲的哨兵位）：

        ┌───┬───┬───┬ ─ ┐
        │ 1 │ 2 │ 3 │ ✗ │   rear 指向那个空格子（3），(3 + 1) % 4 = 0 == front → isFull ✓
        └───┴───┴───┴ ─ ┘
        ↑               ↑
      front=0         rear=3

   ✗ 那个格子：宁可空着，也绝不写入 —— 它就是"空/满"的区分标志
```

**净效果：数组长度 `maxSize`，真实能装的元素个数只有 `maxSize - 1`。** 代码注释里那句「设置数组大小为4，说明数组最大可以存放3个元素」说的就是这件事，`main` 里传 4 是对的用法。

实践口诀：**想存 n 个元素，就传 `n + 1`。**

## 四、绕圈现场：`rear` 是怎么从末尾弹回 0 的（本程序的灵魂）

`maxSize = 4`（真实容量 3 个），按代码一步步走，重点看 **第 ⑤、⑦、⑧** 这三步：

```
① 初始            front=0  rear=0
   ┌────┬────┬────┬────┐
   │    │    │    │    │   isEmpty: rear == front ✓
   └────┴────┴────┴────┘
    ↑f,r

② 放 1  arr[0]=1; rear=(0+1)%4=1
   ┌────┬────┬────┬────┐
   │ 1  │    │    │    │
   └────┴────┴────┴────┘
        ↑r  ↑f

③ 放 2  arr[1]=2; rear=2
④ 放 3  arr[2]=3; rear=3
   ┌────┬────┬────┬────┐
   │ 1  │ 2  │ 3  │    │      rear=3 正好停在牺牲位上（这一格故意不装东西）
   └────┴────┴────┴────┘
    ↑f              ↑r
   有效个数 = (3 + 4 - 0) % 4 = 3 → 已经是满编状态

⑤ 再放 4 → 判满：(3 + 1) % 4 = 0 == front ✓ 满 → 打印"队列已满"，只能干看着
⑥ 取出 1 → value = arr[front=0] = 1；front = (0 + 1) % 4 = 1
   ┌────┬────┬────┬────┐
   │(1) │ 2  │ 3  │    │      front=1, rear=3 → 有效个数 = (3 + 4 - 1) % 4 = 2
   └────┴────┴────┴────┘
         ↑f         ↑r
   arr[0] 里那个 1 还躺着，但它已经不在有效区间了（出队从不擦数据）

⑦ ⭐ 再放 4 —— 判满：(3 + 1) % 4 = 0，而 front 已经是 1，0 != 1 → 不满，放行！
   arr[rear=3] = 4;  rear = (3 + 1) % 4 = 0    ← 先写自己指着的 arr[3]，然后 rear 撞到天花板绕回 0
   ┌────┬────┬────┬────┐
   │ ↑r │ 2  │ 3  │ 4  │      front=1, rear=0 → 有效个数 = (0 + 4 - 1) % 4 = 3，又满编了
   └────┴────┴────┴────┘
   ⭐ 这就是上一版永远做不到的事：一次性队列在此刻会直接报"队列已满"，环形队列把绕回来的空间用上了

⑧ 再放 5 —— 判满：(0 + 1) % 4 = 1 == front(1) ✓ 是满 → 拦住，打印"队列已满"
   此刻被牺牲的格子变成了 arr[0]（里面还残留着早已出队的那个 1，但它在有效区间之外，不算数据）
   有效区间永远是"从 front 起绕圈数 3 格"：arr[1] → arr[2] → arr[3]
```

**一个必须建立的心智模型：牺牲位不是固定的某一格，而是「`rear` 当前指着的那一格」**，它跟着指针在圈上漂移（第 ④ 步在 `arr[3]`，第 ⑧ 步漂到了 `arr[0]`）。判满那句 `(rear + 1) % maxSize == front` 翻译成大白话就是：**「我再往前走一步就要撞上队首了，说明我已经满了」** —— 留一步的距离，就是为了有这一步可以"撞"。

## 五、有效元素个数公式：为什么要 `+ maxSize`

```java
public int getMaxSize() {
    // rear = 1, front = 0, maxSize = 3
    // (1 + 3 - 0) % 3 = 1
    return (rear + maxSize - front) % maxSize;
}
```

绕圈之后，`rear` 不一定比 `front` 大了（一个在圈上跑得快，可能已经超过 front，也可能绕回来了），直接 `rear - front` 会算出**负数**：

```
情况 A：rear 还没绕回，rear ≥ front          rear=3, front=1 → 3 - 1 = 2 ✓ 正常
情况 B：rear 已经绕回起点之前，rear < front    rear=0, front=1 → 0 - 1 = -1 ✗ 荒谬

所以先加一个 maxSize 垫成非负数，再取模：
   (rear + maxSize - front) % maxSize
   (0 + 4 - 1) % 4 = 3 ✓   ← 正确：牺牲位之外，绕圈占了 3 格（arr[1]、arr[2]、arr[3]）
```

`+ maxSize` 是个**万金油垫底**：`(rear - front)` 最小可能是 `-(maxSize-1)`，加一个 `maxSize` 后必定 ≥ 1，取模结果就对了。这是所有"环形下标"计算的通用套路，记住这个式子以后遇到类似场景（环形缓冲区、取模计时、星期几推算）都能套。

Java 里如果不想垫，也可以用 `Math.floorMod(rear - front, maxSize)`，它天生处理负数。

## 六、`showQueue`：绕圈遍历的正确姿势

因为 `rear` 可能已经绕到 `front` 前面了，不能用 `for (i = front; i < rear; i++)`（那样一个空转就退出）。代码的解法很巧：

```java
for (int i = front; i < front + getMaxSize(); i++) {
    System.out.printf("arr[%d]=%d\n", i % maxSize, arr[i % maxSize]);
}
```

两层意思：

1. **循环次数 = 有效元素个数**（`getMaxSize()`），而不是靠"从 front 跑到 rear" —— 这样绕圈与否都能正确数出该打印几个。
2. **`i` 允许超过 `maxSize-1`，落到数组外时靠 `% maxSize` 绕回来**：`i` 是"逻辑下标"，`i % maxSize` 才是"物理下标"。

图示（`maxSize = 4`，`front = 2`，队里 3 个元素）：

```
   逻辑下标 i :   2    3    4          （i 会涨到 4，越界）
                 ↓    ↓    ↓
   物理下标 i%4:  2    3    0          ← 绕回数组头部
                 ┌────┬────┬────┐
    arr      =   │ 5  │ 2  │ 3  │ 4   打印顺序：arr[2]=3 → arr[3]=4 → arr[0]=5
                 └────┴────┴────┘
                  ↑0        ↑2=front   ↑r=1
   绕圈后"从头开始看"的视觉效果，正是靠 i % maxSize 实现的
```

> 小优化：`i < front + getMaxSize()` 每轮都会重算一次 `getMaxSize()`。虽然结果不变（循环体不改 `rear`），但更清晰的写法是先 `int size = getMaxSize();` 存下来，或写成 `for (int i = 0; i < size; i++) { int idx = (front + i) % maxSize; ... }`。

> ⚠️ 一个真实的瑕疵：这行注释 `// 显示目前队列的所有数据，因为front不一定指向队列的第一个元素` 是从**一次性队列**那边复制过来的，在这份代码里 `front` **恰恰就是**指向第一个元素。过时注释比没注释更容易误导人，建议改成「因为队列可能绕圈，rear 不一定在 front 右边，所以按有效个数遍历并用 %maxSize 落到真实下标」。

## 七、`getQueue` 为什么要"先存临时变量"

```java
int value = arr[front];     // 1 先把 front 对应的值保留到临时变量
front = ++front % maxSize;  // 2 front 后移（取模，保证在 0..maxSize-1 之间循环）
return value;               // 3 返回临时保存的值
```

顺序不能倒过来：如果先 `front = ++front % maxSize` 再 `return arr[front]`，返回的就是**第二个**元素了（把队首跳过了一次）。这是所有"取并前进"操作的通用要求：**先用旧位置取值，再移动指针。**

顺带三个细节：

- `front = ++front % maxSize;` 里 `++front` 是**前置自增**，优先级高于 `%`，等价于 `front = (front + 1) % maxSize`。写成 `front = front++ % maxSize` 就错了（后置自增返回旧值，`(旧值) % maxSize` 赋回给一个刚自增过的变量，绕圈会失效）。
- 同样没有把 `arr[front]` 清 0 —— 跟一次性队列一样，出队只是移动指针，旧数据留在格子里。这在功能上无害，但**如果数组存的是对象引用，会形成"无法回收的引用"**（memory leak），JDK 的 `ArrayDeque` 在 `poll` 里会显式 `elements[tail] = null`。
- `isEmpty()` 时抛 `RuntimeException("队列为空，不能取数据")`，被 `main` 里 `case 'g'` 的 `catch (Exception e)` 接住 —— 机制和 [队列.md 第六节](./队列.md) 完全一致，这里不再重复。这版的 `case 'a'` **仍然没给 `scanner.nextInt()` 套 try**，输入字母照样崩；`case 'e'` 里补了 `scanner.close()`，比上一版规整了些。

## 八、命名坑 + 一次性队列全维度对照

### 坑：`getMaxSize()` 这名字起反了

```java
private int maxSize;                    // 数组长度（含牺牲位）
public int getMaxSize() { ... }         // 返回的是【当前有效元素个数】
```

一个叫 `maxSize` 的字段和一个叫 `getMaxSize()` 的方法摆在一起，前者是"容量"、后者是"当前装了几个"，**语义完全不同却撞名**。推算容量、有效个数时极易误判。建议改名 `size()` 或 `validSize()`，跟 JDK 的 `Collection.size()` 习惯对齐；`maxSize` 则可以叫 `capacity`。

### 全维度对照（把两份文档的结论合并看）

| 维度 | `ArrayQueue`（一次性） | `CircleArrayQueue`（环形） |
|---|---|---|
| `front` 起点 / 含义 | -1 / 队首的**前一格** | 0 / 队首**本身** |
| `rear` 起点 / 含义 | -1 / 队尾**本身** | 0 / 队尾的**后一格** |
| 判空 | `rear == front` | `rear == front`（没变，但语义变了：0 号位现在也是有效位） |
| 判满 | `rear == maxSize - 1` | `(rear + 1) % maxSize == front` |
| 有效个数 | `rear - front` | `(rear + maxSize - front) % maxSize` |
| 入队 | `rear++` → `arr[rear]=n` | `arr[rear]=n` → `rear=++rear%maxSize` |
| 出队 | `front++` → `return arr[front]` | `value=arr[front]` → `front=++front%maxSize` → `return value` |
| 显示队头 | `arr[front + 1]` | `arr[front]` |
| 空间复用 | ❌ 出队腾出的格子再也用不上，用完即废 | ✅ 绕圈复用，可无限次进出 |
| 真实容量 | `maxSize`（一次性） | `maxSize - 1`（随时可用） |
| 单步复杂度 | O(1) | O(1) |

## 九、"牺牲一格"不是唯一解

面试如果追问"能不能不浪费这个格子"，有三种主流答案：

```
方案 A（本程序）：牺牲一个格子
   判空 rear == front      判满 (rear+1)%maxSize == front
   ├ 优点：只靠两个指针，无额外字段，代码最短
   └ 缺点：浪费 1 个槽；容量 = maxSize - 1，容易算错（传 4 只能存 3）

方案 B：额外维护一个 size 计数
   判空 size == 0          判满 size == maxSize
   ├ 优点：格子全用上，语义直白，size 顺便还能当有效个数
   └ 缺点：多一个字段要在 add/poll 两侧同步维护，漏改一处就出现"幽灵不一致"

方案 C：单调递增计数器 + 掩码（工业级做法）
   head/tail 只增不减、永不取模，用 tail - head 直接得元素个数
   访问数组时才 index = counter & (capacity - 1)   （容量必须取 2 的幂）
   ├ 优点：无牺牲位；减法天然表示"跑了多远"，多线程下能安全地各写一个指针（Disruptor、DPDK ring buffer、LMAX）
   └ 缺点：要求容量是 2 的幂；计数器溢出要特殊处理（long 一般够用）
```

JDK 的 `ArrayDeque` 用的是另一条路：`head == tail` 表示空，快满时**直接扩容**（数组翻倍重排），所以既不牺牲格子也不需要 size 字段 —— 它把"浪费一格"换成了"偶发 O(n) 的扩容"。看源码时你会发现它的 `tail` 同样是"最后一个元素的后一格"，跟你这个 `rear` 定义一模一样。

## 十一、一句话记住环形队列

> **把数组头尾接成一个圈，靠 `% maxSize` 让 `front`、`rear` 绕圈走，出队腾出的槽位能被重新装上数据；为了让 `rear == front` 不歧义，故意牺牲一个格子，于是"传 n 只能存 n-1"；`rear` 指"下一个空位"所以入队要先写后移，`front` 指"队首本身"所以取头是 `arr[front]`；数有效长度时先 `+ maxSize` 再取模，防止绕圈后的减法变成负数。**

## 十二、往下学什么

1. **改造成方案 B / C**：加 `size` 字段去掉牺牲位，把构造参数 `4` 改成真能装 4 个；再试试"单调计数器 + `& (cap-1)`"，体会工业实现的差别。
2. **把 `getMaxSize()` 改名**（`size()`），并修正第六节指出的那两句过时注释 —— 命名和注释同步也是编程能力的一部分。
3. **双端队列 Deque**：既然会绕圈了，加上"头部插入 + `rear-1` 取模"（注意 `rear - 1` 可能为负，要用 `(rear - 1 + maxSize) % maxSize` 或 `Math.floorMod`），你就得到了 `ArrayDeque` 的雏形。
4. **链表队列**：不用定容量、不用绕圈、不用牺牲位，理解"数组换空间连续性，链表换动态长度"这笔交易（节点写法见 [单链表.md](../linkedlist/%E5%8D%95%E9%93%BE%E8%A1%A8.md)）。
5. **阻塞队列**：`LinkedBlockingQueue` 里入队出队是线程安全的，绕圈逻辑几乎不变，多的是锁和 `wait/notify`。
