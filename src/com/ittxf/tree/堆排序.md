# 堆排序（用数组表示的完全二叉树）

> 对应程序：[HeapSort.java](./HeapSort.java)
> 为什么放在 `tree` 包而不是 `sort` 包：堆排序的"堆"就是一棵**用数组下标当指针的完全二叉树**（`2i+1`、`2i+2`），用的正是 [二叉树.md](./%E4%BA%8C%E5%8F%89%E6%A0%91.md) 第二节那套下标关系。它是 [排序.md](../sort/%E6%8E%92%E5%BA%8F.md) 第十三节列的"往下学"里第一个补上的。
> 下文毫秒数都是本机（JDK 21）实测：数据用 `new Random(1994)` 生成的 80000 个 `[0, 80000]` 整数（与 排序.md 第十节同一份），预热一次后跑 7 次取中位数。

---

## 一、先看结论

| 指标 | 实测 |
|---|---|
| 8 万随机 | **5.51 ms**（最小 5.21 / 最大 5.69） |
| 8 万已升序 / 完全逆序 | 3.35 ms / 3.58 ms |
| 2 万已升序 / 完全逆序 | 0.80 ms / 0.82 ms |
| 8 万全相同 | **0.13 ms** ← 快得反常，见第五节 |
| 与 `Arrays.sort` 结果一致 | ✅ 以上每一组都一致 |
| 额外空间 | O(1)（只有 `temp`、几个下标） |
| 稳定？ | ❌ 不稳定，实测见第五节 |

放进 排序.md 那张大表里横向看（同一份 8 万随机数据）：

```
冒泡 6684  |  选择 1108  |  插入 234（首轮 705）  |  希尔交换 3244
希尔移动 7.1  |  快排 5.9  |  堆排 5.5  |  归并 6.3  |  基数 2.1  |  Arrays.sort 3.2
```

**堆排和快排、归并、希尔移动法挤在同一个 5~7 ms 档**，但它有两个别人同时不具备的性质：**最坏也是 O(n log n)**（快排最坏 O(n²)）**且只用 O(1) 额外空间**（归并要 O(n) temp、基数要 10n 的桶）。这就是"要最坏保证又不肯花内存"时选它的原因。

## 二、整个算法就两步

```java
public static void heapSort(int[] arr) {
    // ① 建堆：从最后一个非叶子节点开始，自底向上逐个下沉
    for (int i = arr.length / 2 - 1; i >= 0; i--) {
        adjustHeap(arr, i, arr.length);
    }
    // ② 反复"堆顶换到末尾 + 堆缩小一格 + 重新调整堆顶"
    for (int i = arr.length - 1; i > 0; i--) {
        temp = arr[i]; arr[i] = arr[0]; arr[0] = temp;   // 最大值沉到 i
        adjustHeap(arr, 0, i);                           // 注意 length 传的是 i，堆变小了
    }
}
```

要排**升序**，建的却是**大顶堆**（父 ≥ 子）。反直觉但很自然：大顶堆的堆顶是最大值，每轮把最大值换到数组末尾，末尾就越攒越大 —— **升序排序从尾部开始填**。想降序就建小顶堆。

`arr.length / 2 - 1` 是最后一个非叶子节点的下标：完全二叉树里最后一个叶子是 `n-1`，它爹就是 `(n-1-1)/2`，化简后正好 `n/2 - 1`。从它开始往前逐个 adjust，等于**自底向上**把每棵子树都调成堆 —— 后面的 adjust 依赖前面已经把更深的子树调好了，顺序反过来（从 0 往后）就白干。

## 三、`adjustHeap`：一次"下沉"

代码注释里那组 `{4, 6, 8, 5, 9}` 分了两步演示，实测跑出来和注释**完全一致**：

```
adjustHeap(arr, 1, 5) → [4, 9, 8, 5, 6]     注释写的 [4,9,8,5,6] ✅
adjustHeap(arr, 0, 5) → [9, 6, 8, 5, 4]     注释写的 [9,6,8,5,4] ✅
```

```java
public static void adjustHeap(int[] arr, int i, int length) {
    int temp = arr[i];                                   // ① 先把要下沉的值存起来
    for (int k = i * 2 + 1; k < length; k = i * 2 + 1) { // ② k 始终是 i 的左孩子
        if (k + 1 < length && arr[k] < arr[k + 1]) k++;  // ③ 右孩子更大就让 k 指向右边
        if (arr[k] > temp) { arr[i] = arr[k]; i = k; }   // ④ 大的往上提，i 跟进到孩子层
        else break;                                      // ⑤ 已经满足堆性质，停
    }
    arr[i] = temp;                                       // ⑥ 最后把原值落在最终位置
}
```

三个点：

1. **①和⑥是"先存后放"**，和 [插入排序](../sort/%E6%8E%92%E5%BA%8F.md) 里必须先存 `insertValue` 是同一个道理：④ 是**赋值覆盖**而不是交换，一路把子节点的值往上抄，最后才把 `temp` 放进落点。整次下沉只做 1 次写落位，比"每层交换一次"少 2/3 的写操作。
2. **`k = i * 2 + 1` 写在 for 的更新段里很关键**。循环体里 `i = k` 先挪了父位置，所以更新段用新的 `i` 重新算左孩子，`k` 就跟着下移一层。写成 `k = k * 2 + 1` 是错的（那是"孩子的孩子"，跳太快）。
3. **`length` 是逐渐缩小的**。第②步里 `adjustHeap(arr, 0, i)` 传的是 `i` 而不是 `arr.length` —— 因为 `[i, n)` 已经是排好的部分，不能再被拉回堆里。少写这个参数就会把已排好的尾巴搅乱。

## 四、复杂度：为什么建堆是 O(n) 而不是 O(n log n)

| 阶段 | 代价 | 说明 |
|---|---|---|
| 建堆 | **O(n)** | 不是 `n/2 × log n`：越靠下的节点子树越矮，能下沉的层数越少。`Σ (层数 × 该层节点数)` 收敛到 O(n) |
| n-1 轮"交换 + 下沉" | O(n log n) | 每轮一次交换 + 一次最多 log n 层的下沉 |
| 总计 | O(n log n)，**最好/最坏/平均都是** | 这是它相对快排的硬优势 |
| 空间 | O(1) | 原地；没有递归（`adjustHeap` 是循环写的） |
| 缓存 | 差 | 下沉时按 `2i+1` 跳着访问，数组越远跳得越狠，Cache 命中率低 |

最后那条"缓存差"就是**实测里堆排 5.51 ms 打不过 `Arrays.sort` 3.24 ms** 的主要原因 —— 双轴快排的扫描是顺序访存。工程上这也是 `Arrays.sort` 不用堆排当主力的原因；堆排的真正用武之地是"最坏保证 + O(1) 空间"或者 **Top-K**。

## 五、两个实测细节

### 稳定性：能直接测出来

`int[]` 里相等的值不可区分（[排序.md](../sort/%E6%8E%92%E5%BA%8F.md) 第七节讲归并时说过），所以探针给每个元素编了个"键 + 原始下标"：`arr[i] = (i % 4) * 100 + (99 - i)`，键只取 4 种，键内靠低位区分。堆排后把每个元素的**原始下标**打出来：

```
12 8 4 0 | 13 9 5 1 | 14 10 6 2 | 15 11 7 3
```

每个键内部是**递减**的 —— 原来在前的反而排到了后面，**不稳定**，实测坐实。

### 全相同数据为什么只要 0.13 ms

`adjustHeap` 的 ⑤ 那句 `else break`：全相同时 `arr[k] > temp` 恒不成立，**每次下沉一层就立刻退出**，于是建堆和 n-1 轮调整全都退化成"看一眼就走"，只剩交换本身。所以堆排序对"已排好/全相同"这类数据也有很好的常数表现（但注意它**不会**像冒泡那样整趟跳过，交换照做 n-1 次）。

### 边界

实测：`heapSort(new int[0])` 和 `heapSort(new int[]{7})` 都平安返回（两个 for 的初始条件 `arr.length/2-1 = -1`、`i = 0 > 0` 都不成立，直接不干活）；`{4,6,8,5,9}` → `[4,5,6,8,9]`、`{5,3,5,1,5,3}` → `[1,3,3,5,5,5]` 都正确。**比 基数排序 空数组就抛异常 稳当。**

## 六、动手验证剧本

```powershell
javac -encoding UTF-8 -d out (Get-ChildItem -Recurse src -Filter *.java).FullName
java -cp out com.ittxf.tree.HeapSort      # 8 万个随机数，打印耗时
```

| 实验 | 怎么改 | 会看到什么 | 印证哪一节 |
|---|---|---|---|
| 1 | 把 `main` 里的数组换成 `{4,6,8,5,9}`（放开注释那行） | 排序后自己加一句打印，得到 `[4, 5, 6, 8, 9]` | 五节 |
| 2 | 把建堆循环改成 `for (int i = 0; i < arr.length/2; i++)`（正着来） | 结果**仍然正确**，但多做了一堆无用的下沉（后面的 adjust 会重排前面调好的）；改成只调 `adjustHeap(arr,0,n)` 一次就会错 | 二节 |
| 3 | 把 `adjustHeap(arr, 0, i)` 的 `i` 改成 `arr.length` | 已排好的最大值被重新拉回堆里，结果错 | 三节 3） |
| 4 | 把 ④ 的 `arr[i] = arr[k]` 改成"三行交换" | 结果仍正确，但耗时明显上涨（写操作多了 3 倍）—— 和希尔交换法 vs 移动法是同一个教训 | 三节 1） |
| 5 | 把 `>` 改成 `>=`（`arr[k] >= temp`） | 结果仍正确，但相等元素会被无谓地搬动，稳定性实验的下标顺序会变 | 五节 |

第 3、4 条最有体感：一个是"少缩一格就错"，一个是"写法不同就差几倍"。

## 七、一句话记住堆排序

> **堆排序 = 先把数组原地建成大顶堆（从 `n/2-1` 往前逐个下沉，建堆是 O(n) 不是 O(n log n)），再反复"堆顶和末尾交换 + 堆缩小一格 + 重新调整堆顶"；升序配大顶堆、从尾部开始填；`adjustHeap` 靠"先存 temp、大的往上抄、最后落位"把一次下沉压到 1 次写；`length` 参数必须跟着缩小否则会把排好的尾巴搅乱；它是唯一一个"最坏 O(n log n) + O(1) 额外空间"的组合，代价是跳着访问导致缓存不友好，实测 5.51 ms 跑不过 `Arrays.sort` 的 3.24 ms；实测不稳定（同键元素原始下标变成 12 8 4 0）。**

## 八、往下学什么

1. **Top-K / 优先队列**：堆排序最实用的形态不是排序，是"从 n 个里取前 k 个" —— 维护一个大小为 k 的小顶堆，O(n log k)。JDK 的 `PriorityQueue` 就是（小顶堆，`offer`/`poll`），拿它写一遍 Top-K 再回来看这篇会有新理解。
2. **为什么工程实现不用堆排**：`Arrays.sort(int[])` 是双轴快排，只在"递归太深疑似退化"时才**临时**切到堆排兜底 —— 去看 `java.util.DualPivotQuicksort` 里那个 `heapSort` 分支（我在 排序.md 第九节提过它的 `MAX_RECURSION_DEPTH` 保护）。
3. **建堆 O(n) 的证明**：`Σ (h - i) × 2^i` 那个级数，动手推一遍就知道为什么不是 O(n log n)。
4. **败者树 / 多路归并**：外部排序里用堆来选"当前 k 个归并段的最小值"，是堆排序思想在磁盘上的形态，接 排序.md 第十三节。
