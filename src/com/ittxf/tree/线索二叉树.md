# 中序线索化二叉树

> 对应程序：[ThreadedBinaryTreeDemo.java](./ThreadedBinaryTreeDemo.java)
> 前置阅读：[二叉树.md](./%E4%BA%8C%E5%8F%89%E6%A0%91.md) —— 那篇末尾算过一笔账：n 个节点的二叉树里有 **n+1 个空指针**，本篇要干的就是把这些空位拿来存"前驱"和"后继"。
> 本篇所有指针状态、遍历顺序、异常都是本机（JDK 21）实跑/探针实测得到的。探针里为了看清中间状态，临时把每个节点的 `leftType/rightType` 打了出来。

---

## 一、要解决的问题

普通二叉树想中序遍历，只有两条路：递归（每层一个栈帧，O(h) 空间）或者自己拿显式栈模拟。**但叶子和空孩子那一侧的指针域全都是 null，白白空着**。中序线索化的想法：

* 某节点的**左孩子为空** → 让左指针指它的**中序前驱**；
* 某节点的**右孩子为空** → 让右指针指它的**中序后继**；
* 每个节点加两个标志位 `leftType`/`rightType`：`0` 表示"这是真孩子"，`1` 表示"这是线索"。

这样遍历就变成"顺着指针走"，不需要栈。代价是每个节点多两个 int，以及**一旦混用，真孩子和线索会互相冒充**——本篇第五、六节实测到的两个问题都是这个代价。

## 二、这棵树和线索化后的完整指针表

`main` 里搭的是一棵 7 节点完美二叉树（注意人名和上一篇不同，2 号在这里是卢俊义）：

```
          1 宋江
        /        \
    2 卢俊义    3 吴用
    /   \       /   \
 4 公孙胜 5 关胜 6 林冲 7 武松
```

它的中序序列是 `4 2 5 1 6 3 7`（实测递归 `inOrder()` 打出来的，也是下面线索链走出来的，两边对得上）。

`threadInOrder()` 跑完之后，7 个节点的指针状态实测如下：

| 节点 | leftType → 左指针 | rightType → 右指针 | 说明 |
|---|---|---|---|
| 1 | 0 → 节点2 | 0 → 节点3 | 根两个孩子都齐，用不上线索 |
| 2 | 0 → 节点4 | 0 → 节点5 | 同上 |
| 3 | 0 → 节点6 | 0 → 节点7 | 同上 |
| 4 | **1 → null** | **1 → 节点2** | 中序第一个，**没有前驱**所以左还是 null；后继是 2 |
| 5 | **1 → 节点2** | **1 → 节点1** | 前驱 2、后继 1 |
| 6 | **1 → 节点1** | **1 → 节点3** | 前驱 1、后继 3 |
| 7 | **1 → 节点3** | **0 → null** | 前驱 3；中序最后一个，**没有后继**，右指针留空 |

**7 个节点、14 个指针域，其中 6 个被填成了真线索**（4→右指 2、5→左指 2、5→右指 1、6→左指 1、6→右指 3、7→左指 3），另外 2 个是合法端点（4 的左：中序第一个，无前驱；7 的右：中序最后一个，无后继）。`6 + 2 = 8 = n + 1`，正好对上上一篇那笔空指针的账。

`main` 里那两行测试取的就是 5 号这一格：

```
5号节点的前驱节点是：HeroNode{no=2, name='卢俊义'}
5号节点的后继节点是：HeroNode{no=1, name='宋江'}
```

## 三、`threadInOrder` 的三段结构

```java
public void threadInOrder(HeroNode2 node) {
    if (node == null) return;
    // (一) 先线索化左子树
    if (node.getLeftType() == 0) threadInOrder(node.getLeftChild());
    // (二) 处理当前节点
    if (node.getLeftChild() == null) {        // 左空 → 挂前驱
        node.setLeftChild(preNode);
        node.setLeftType(1);
    }
    if (preNode != null && preNode.getRightChild() == null) {   // 前一个的右空 → 挂后继
        preNode.setRightChild(node);
        preNode.setRightType(1);
    }
    preNode = node;                            // !!! 走一步就把"前驱"往前挪
    // (三) 再线索化右子树
    if (node.getRightType() == 0) threadInOrder(node.getRightChild());
}
```

三个点值得单独说：

1. **"给 node 挂前驱"和"给 preNode 挂后继"是同一根指针的两面**，代码里分开写：左指针挂在当前节点上（因为前驱一定已经处理过、就是 `preNode`），右指针挂在 `preNode` 上（因为后继要等它自己被访问到时才知道）。
2. **`preNode = node` 这句的位置是铁律**，必须夹在"处理当前节点"和"进右子树"之间。放早了，右子树还没走，`preNode` 就不是中序意义上的前驱；放晚了，下一个节点拿到的前驱会差一位。这和 [迷宫与回溯.md](../recursion/%E8%BF%B7%E5%AE%AB%E4%B8%8E%E5%9B%9E%E6%BA%AF.md) 里"回溯复位的位置决定对不对"是同一类问题。
3. **第 63、81 行那两个 `getLeftType() == 0` / `getRightType() == 0` 判断不是多余的**：如果直接写 `threadInOrder(node.getLeftChild())`，一旦某个节点的左指针已经是线索（指向前驱），递归就会顺着线索倒着走回去，当场死循环。这两处守卫的是"别把线索当孩子的路走" —— 但只守住了**递归下降**这一侧，下一节会看到另一侧没守住。

## 四、怎么"顺着线索走"：`threadList()`

线索化的目的就是这个，`ThreadedBinaryTreeDemo.threadList()` 干的就是这件事，规则两条：

1. 找**中序第一个**：从根开始一路走 `leftType == 0` 的左指针，走到头；
2. 每步之后问一句"右指针是线索还是真孩子"：
   * `rightType == 1` → 右指针就是后继，直接过去，**不用再往左钻**；
   * `rightType == 0` → 右指针是真孩子，进去之后再一路向左钻到底。

实测走一圈：

```
4 2 5 1 6 3 7（7 步，自然走到 null 结束）
```

和第 二 节的递归中序完全一致。**全程没有栈、没有队列，只有一根指针** —— 这就是线索化的全部卖点。

`threadList()` 的实现就是这两条：外层 `while (node != null)`，先用 `while (node.getLeftType() == 0) node = node.getLeftChild();` 钻到最左叶子，打印，再用 `while (node.getRightType() == 1)` 顺着右线索一路吐，最后 `node = node.getRightChild()` 跨到下一棵子树。实测 `main` 的输出：

```
使用线索化的方式遍历线索二叉树：
HeroNode{no=4, ...} no=2  no=5  no=1  no=6  no=3  no=7      ← 即 4 2 5 1 6 3 7
```

**顺序和第二节递归 `inOrder()` 完全一致** ✅。

第 2 条里"`rightType == 1` 就别再往左钻"这一步非常容易写错：探针第一版就是无脑"进右指针后一路向左"，结果 4→2→（2 的左是 4）→4……在 2 和 4 之间来回，打出来是 `4 4 4 4 4 …`。

⚠️ 顺带一处要改的：`main` 里两处注释写的是"原中序遍历：4 5 2 1 6 7 3"和"`threadList(); // 4 5 2 1 6 7 3`"，但实测输出是 **`4 2 5 1 6 3 7`**（`5` 和 `2`、`7` 和 `3` 位置互换了）。`main` 自己那两行"5 号的前驱是 2、后继是 1"也只有 `4 2 5 1 …` 才成立 —— 注释是笔误，程序是对的。

## 五、⚠️ 线索化之后，`inOrder()` / `preOrder()` 这些老遍历方法全都不能用了

`HeroNode2` 里那三个遍历方法判的都是 `this.leftChild != null`，**不看 `leftType`**。线索化之后，`4.rightChild` 是指回 2 的线索、`5.leftChild` 是指回 2 的线索，"非空"永远成立，于是递归就在父子之间来回弹。实测：

| 调用 | 实测结果 |
|---|---|
| 线索化前 `inOrder()` | 正常打完 `4 2 5 1 6 3 7` 七行 |
| **线索化后 `inOrder()`** | 从第一行开始反复打印 `HeroNode{no=4...}`，探针截到 118 行还在继续；同样的调用再跑一次直接 **`StackOverflowError`** |
| **线索化后 `preOrder()`** | 输出 `1 2 4 2 4 2 4 …`，同样停不下来（4 的右线索指回 2） |

根因用一张图说完：

```
   节点2：leftChild → 4（type=0，真孩子）
   节点4：rightChild → 2（type=1，是线索！）
   递归 inOrder：进 2 → 进 2 的左孩子 4 → 4 的左没了，打印 4 → 进 4 的"右孩子" → 又回到 2 → 再进 2 的左孩子 4 → …
```

**结论：一旦线索化，这套类上就只应该保留"顺线索走"那种遍历。** 想同时保留递归遍历，就得在每个 `!= null` 判断上补一个 `type == 0` —— 也就是把第 63、81 行那两处的写法搬到 `inOrder`/`preOrder`/`postOrder` 里去。

### 顺带：`deleteNode` 也一样会炸

`deleteNode` 找目标时同样只看 `!= null`。实测在一棵已经线索化的 7 节点树上：

| 调用 | 实测结果 |
|---|---|
| `deleteNode(3)`（3 是根的右真孩子） | 正常返回，`1` 的右指针置空 |
| `deleteNode(4)` | **`StackOverflowError`** |
| `deleteNode(6)` | **`StackOverflowError`** |
| 同一棵树**不**线索化，`deleteNode(6)` | 正常返回 |

为什么删 4 会炸：目标在 `2.leftChild` 处命中并置空后，`return` 只结束**当前这一层**；`deleteNode` 没有"已经删掉了"的返回值往上传，父层（节点 1）随后照样执行 `this.rightChild.deleteNode(no)` 去右子树找。没线索时右子树是棵树，走完就结束；**有线索时右子树里到处是指回祖先的指针，于是 2↔5↔1 来回弹，爆栈**（异常栈里第 369、372 行交替出现，正是"递归左 → 递归右"那两句）。

所以这是同一个病根的第二个症状：**`deleteNode`/三种遍历都按"纯树"写的，`threadInOrder` 把结构改成了带环的图。**

## 六、⚠️ `threadInOrder()` 不能跑第二次：`preNode` 没有复位

代码里 `preNode` 是 `ThreadedBinaryTree` 的**实例字段**，线索化结束时它停在**最后一个访问的节点**（7 号）上，而方法入口没有 `preNode = null`。实测连着调用：

| 第几次调用 | 节点 4 的左指针 | 节点 7 的右指针 | 顺线索走一圈 |
|---|---|---|---|
| 第 1 遍 | `null`（type=1） | `null`（type=0） | `4 2 5 1 6 3 7` ✅ 7 步自然结束 |
| 第 2 遍 | **节点 7**（type=1） | **节点 4**（type=1） | `4 2 5 1 6 3 7 4 2 5 1 6 3 7 …` 走不出去 |
| 第 3 遍 | 节点 7 | 节点 4 | 同第 2 遍，不再继续变化 |

第二遍进来时 `preNode` 还指着 7 号，处理第一个节点（4 号）就执行了 `node.setLeftChild(preNode)` → **4 的左指针变成 7**；等到处理 7 号时，`preNode(7 的前一个)` 的右指针为空，被挂成 `7.setRightChild(4)`，**首尾接成了一个环**。第 63/81 行那两个 `type == 0` 守卫只挡住"往下钻"，挡不住"当前节点左指针本来就空、直接挂 preNode"这条路径。

修法只有一行：`threadInOrder()` 这个重载入口里先 `this.preNode = null;`。

## 七、复杂度与前后序线索化

| | 时间 | 额外空间 |
|---|---|---|
| 中序线索化 | O(n) | O(h) 递归栈（`preNode` 是 O(1)） |
| 顺线索找后继 | 均摊 **O(1)** | **O(1)**，不需要栈 |
| 顺线索走完整个树 | O(n) | O(1) |
| 递归中序遍历 | O(n) | O(h)，最坏 O(n) |

两个"均摊 O(1)"才是线索化的收益所在：绝大多数节点直接吃右线索，只有进真右孩子时才要往左钻一次，而每次"往左钻"走过的边在整轮遍历里只走一遍。

最后一点必须点破，否则容易踩坑：**中序的"前驱/后继"能用空指针就近表示，是因为中序里"左孩子的最后一个"和"右孩子的第一个"正好落在空位上**。前序、后序线索化就不是这个便利结构 —— 后序里"某节点的前驱可能是它的左孩子的右孩子"，一个空位装不下；这也是 `threadPreOrder`/`threadPostOrder` 通常还要额外带一个 `parent` 指针（或者干脆只在线索树上再存一份顺序）的原因。本篇只做了中序版。

## 九、一句话记住线索化

> **线索化就是把 n+1 个空指针改成前驱/后继，配两个 `type` 位说明"这根指针是孩子还是线索"；`preNode = node` 必须卡在"处理当前节点"之后、进右子树之前；递归下降时要用 `type == 0` 守卫，别把线索当路走；顺线索遍历的代价是均摊 O(1) 时间、O(1) 空间，规则是"右指针是线索就直接跟，是真孩子才进去再一路向左"；两个实测代价 —— 线索化之后 `inOrder`/`preOrder`/`deleteNode` 全部会顺线索绕回祖先爆栈，`preNode` 是实例字段又没复位，跑第二遍会把首尾接成一个环。**
