## 一、为什么需要链表：先把数组的账算清楚

数组的毛病在前面几篇里已经吃过两次亏了：

- [稀疏数组.md](../sparsearray/%E7%A8%80%E7%96%8F%E6%95%B0%E7%BB%84.md)：`new int[11][11]` 一旦定死就不能改，空间按最大情况预支。
- [队列.md](../queue/%E9%98%9F%E5%88%97.md) 第五节：数组队列的 `front`/`rear` 只能往后走，出队腾出的格子**再也用不上**（假满），逼得环形队列用 `%` 绕圈。

数组的通病就一句话：**格子在内存里挨着排，所以位置一固定，"挪东西"就是硬成本。**

```
数组：内存里连续，下标 = 起点 + i×元素大小
 ┌───┬───┬───┬───┬───┬───┐
 │ 1 │ 2 │ 3 │ 4 │   │   │   想在中间塞一个 9？后面全部往后挪一格
 └───┴───┴───┴───┴───┴───┘     想删掉 3？后面全部往前挪一格
  0   1   2   3   4   5      ↑ 空位（容量已经焊死）

链表：内存里爱在哪在哪，靠"我的下一个是谁"这根线串起来
 ┌─────┐    ┌─────┐    ┌─────┐
 │ 1 │next├──► 3 │next├──► 4 │next├──► null
 └─────┘    └─────┘    └─────┘
   数据+指针 = 一个节点（node）

 插入 9？把线改一改就行，一个字节的数据都不用搬：
 ┌─────┐    ┌─────┐    ┌─────┐    ┌─────┐
 │ 1 │──┼──►│ 9 │──┼──►│ 3 │──┼──►│ 4 │──┼──► null
 └─────┘    └─────┘    └─────┘    └─────┘
```

代价也摆在明面上：**数组随机访问 O(1)，链表必须从头一路顺着线走过去，第 i 个就是 O(i)。**

| 操作 | 数组 | 单链表 |
|---|---|---|
| 按下标读第 i 个 | **O(1)** | O(i) 只能顺藤摸瓜 |
| 已知前驱、插入/删除 | O(n)（要挪后面全部） | **O(1)**（改两根线） |
| 容量 | 定死 | 要多少给多少 |
| 内存 | 连续，缓存友好 | 分散，每个节点多一个指针的开销 |

一句话：**"读多改少、长度可预估"用数组；"改多、长度不可预估"用链表。**

## 二、这份代码里的三个角色

```java
class HeroNode {          // 节点本体：数据 + 一根指向同类型节点的线
    public int no;        // 编号（唯一，相当于主键）
    public String name;
    public String nickname;
    public HeroNode next; // ★ 这一根线就是链表的全部灵魂
}

class SingleLinkedList {  // 链表管理者：只攥着一个 head，其余全靠线串
    private final HeroNode head = new HeroNode(0, "", "");
    add / addByOrder / update / delete / list
}

class SingleLinkedListDemo {  // 与链表结构无关的算法，全是 static 方法
    getLength / findLastIndexNode / reverseLinkedList / reversePrint / mergeSortedList + main
}
```

这个拆法值得学：**"节点"和"管理节点的人"分开写**，`SingleLinkedList` 只管增删改查，而"求长度 / 找倒数第 k 个 / 反转"这种算法不改变链表归属，放成静态方法（面试时也更接近 LeetCode 的裸链表写法：直接传 `head`）。

## 三、哨兵头节点 head：一个不存数据的空壳

代码注释写得很明确：**「先初始化一个头结点，头结点不要动，不存放具体的数据」**，它的 `no=0`、`name=""` 全是摆设，唯一的价值就是它的 `next`：

```
        哨兵（不存数据，永远待在第一位）              真正的数据从这之后才开始
        ┌────────────┐      ┌──────────┐   ┌──────────┐   ┌──────────┐
   head │ no=0 (空壳)├─────►│ 1 宋江    ├──►│ 3 吴用    ├──►│ 4 林冲    ├─► null
        └────────────┘      └──────────┘   └──────────┘   └──────────┘
           ↑ 链表空的时候，head.next == null
```

**它存在的意义只有一句话：让"第一个节点"不再特殊。**

对比一下不带哨兵（LeetCode 那种 `ListNode head` 直接指向第一个数据节点）的写法：

| 场景 | 带哨兵（本代码） | 不带哨兵 |
|---|---|---|
| 判断空 | `head.next == null` | `head == null` |
| 删除首节点 | 和普通节点一样：`temp.next = temp.next.next` | 必须特判：`head = head.next`，还得把新 head 传出去 |
| 头部插入 | 一样走"插到 temp 后面"的逻辑 | 要改调用者手里的 head 引用 |
| 反转后接回 | `head.next = 新首节点`，一行搞定 | 要把新的头**返回**给调用方（方法签名就得变成有返回值） |

Java 里还有个具体的原因：方法参数是**值传递**，`reverseLinkedList(HeroNode head)` 里给 `head` 重新赋值，外面是看不见的；但改 `head.next` 外面立刻生效 —— 所以**必须有个不动的哨兵当锚点**，所有修改都落在 `head.next` 上。这正是第七节反转能成立的前提。

## 四、五种基本操作，差别全在"temp 从哪起步、跟谁比较"

这是链表最容易写崩的地方。把五个方法的指针策略拉平对比：

| 方法 | temp 起点 | 停止条件 | 为什么这么设计 |
|---|---|---|---|
| `add`（尾插） | `head` | `temp.next == null` | 要挂在最后那个节点**后面**，所以必须停在"最后一个"，即前驱视角 |
| `addByOrder` | `head` | `temp.next.no > no` 或 `temp.next == null` | 插入要改前驱的线，所以找的是**目标位置的前一个节点** |
| `update` | `head.next` | `temp.no == no` | 改的是节点自己的数据，所以直接找**它本身** |
| `delete` | `head` | `temp.next.no == no` | 摘牌必须从前驱下手，所以比较的是 **`temp.next.no`** |
| `list` | `head.next` | `temp == null` | 打印，从第一个真数据开始，跳过哨兵 |

**记法：要"往谁后面插/把谁摘掉"，temp 就停在它前面；要"改谁的数据"，temp 就停在它自己身上。**

### 1. `add`：遍历找尾巴，接上就完事

```java
HeroNode temp = head;
while (true) { if (temp.next == null) break; temp = temp.next; }
temp.next = heroNode;
```

```
遍历到 temp 成为最后一个节点后，只做一件事：
   temp ────► null          temp ────► 新节点 ────► null
   （空出来的那根线，正好给新节点用）
```

`main` 里注释「这里是直接插入尾部不考虑排序」，所以插入顺序是 1、4、2、3 时链表就按 1、4、2、3 排 —— 编号乱的。于是有了下面这版。

### 2. `addByOrder`：有序插入，两步赋值**顺序绝不能反**

```java
heroNode.next = temp.next;   // ① 新节点先"抓住"后面那段
temp.next = heroNode;        // ② 前驱再改线指向新节点
```

```
    插入前：temp ──► X（原本的后继）

    ① heroNode.next = temp.next     新节点先接住 X，此时 X 有两个指针指着它（temp 和 heroNode），安全
       temp ──► X ◄── heroNode
    ② temp.next = heroNode          前驱改线，X 只剩 heroNode 指着，链没断
       temp ──► heroNode ──► X

    ❗ 如果反过来写（先 ② 后 ①）：
       temp.next = heroNode → temp ──► heroNode，而 heroNode.next 还是 null
       此刻 X 已经没有任何指针指着了 → 从 temp 往后只能看到 heroNode → null，X 及其后面整段永久丢失
```

这就是"**先接后断**"的铁律，和第七节反转里的"① 存后路"是同一个道理：**改一根线之前，必须先确认这根线原本连着的对象还有别人能找到它。**

`addByOrder` 还有两个分支值得看：

```java
if (temp.next.no > heroNode.no) break;                    // 找到插入点的前驱
else if (temp.next.no == heroNode.no) { println("编号存在"); return; }  // 拒绝重复编号
```

`main` 里连续 `addByOrder(hero3)` 两次，第二次就是专门用来打印「编号3存在，不能添加」的。

### 3. `update`：先定位，再用 flag 区分"没找到"

```java
HeroNode temp = head.next;      // 改自己的数据，所以从第一个真节点起步
boolean flag = false;
while (true) { if (temp == null) break; if (temp.no == newHeroNode.no) { flag = true; break; } temp = temp.next; }
if (flag) { temp.name = ...; temp.nickname = ...; }   // 只覆盖 name/nickname，no 不动
else println("没有找到编号为...无法修改");
```

两个细节：

- **`no` 不能改**：它是定位用的主键，改了等于把链表顺序搞乱。所以传进来的 `new HeroNode(2, "卢.com", "玉麒麟")` 只用它的 `name`/`nickname` 当"数据包"。
- **`temp == null` 才能退出循环**：这里 temp 是"节点本身"视角，跑到尾巴后面才会是 null。跟 `add` 里判 `temp.next == null` 是两套逻辑，别混。

### 4. `delete`：找前驱，"搭桥"摘牌

```java
HeroNode temp = head;                        // 从哨兵起步，因为要找前驱
if (temp.next.no == no) { flag = true; break; }
...
temp.next = temp.next.next;                  // ★ 一行完成删除
```

```
   删除编号 2：

   temp ──► [2] ──► [3]          temp ──────► [3]        [2] 变成没人指的孤儿
   （比的是 temp.next.no）        temp ──╳       ↑          ↓
                                   搭一座桥绕过 2，     Java 垃圾回收自动收掉

   没有 free/delete：Java 里你只需要"让没有任何指针指向它"，GC 负责其余
```

`delete` 的 `temp.next = temp.next.next` 是链表最漂亮的一招：**不搬任何数据，只是把桥搭过去。** 空链表的两种特判（`head.next == null` 报"链表为空，无法删除"、找不到编号报"没有找到编号为X"）也都补齐了。

### 5. `list`：跳过哨兵，逐个打印

```java
HeroNode temp = head.next;
while (true) { if (temp == null) break; System.out.println(temp); temp = temp.next; }
```

靠 `HeroNode` 重写的 `toString()` 才能直接打印出 `HeroNode [no=1, name=宋江, nickname=及时雨]`。

## 五、`getLength`：能跑，但混进了副作用

```java
while (true) {
    if (temp.next == null) { if (count == 0) System.out.println("链表为空"); break; }
    count++; temp = temp.next;
}
```

从 `head` 起步、判 `temp.next`、只统计有数据的节点 —— 逻辑对（哨兵不计入）。但一个"求长度"的纯查询方法里藏了一句 `println`，代价是：**你只想问个长度，它顺便在屏幕上喊了一句**。这在 `findLastIndexNode` 里已经翻车了（见下面实测输出）：查倒数第几个的时候，控制台莫名其妙先冒出一行"链表为空"。

```java
public static HeroNode findLastIndexNode(HeroNode head, int index) {
    int size = getLength(head);   // ← 空链表时，这里就替你把"链表为空"打印出来了
```

规范做法：查询方法保持**无输出**，把"链表为空"的提示留给调用方或 `list()`。现在 `main` 里跑不出这个问题（链表非空），但我的探针在空链表上把它引出来了：只为了问一下长度，屏幕先抢白一句"链表为空"。

## 六、`findLastIndexNode`：两次遍历法 + 两个实测缺陷

### 思路（注释里写得很全，公式是核心）

```java
int size = getLength(head);
HeroNode temp = head.next;
int pos = size - index;              // ★ 正数第 (size-index+1) 个 = 倒数第 index 个
for (int i = 0; i < pos; i++) temp = temp.next;
```

```
链表：  1    3    4          size = 3，要倒数第 1 个 → pos = 3 - 1 = 2，从第 1 个节点再往后走 2 步
       [1]  [3]  [4]  null
    head.next
       ↑起点(i=0)  → i=1 →  → i=2 →  ✅ 命中 no=4

  校验：倒数第 k 个 = 正数第 (size - k + 1) 个；从"第 1 个"再走 (size - k) 步 = 走 pos 步 ✓
```

代码里那行注释 `// temp 指向链表的第一个节点，不加.next下方循环会重新指向第一个节点，浪费一次循环机会`，说的就是"起点已经算第 0 步，所以走 `pos` 次而不是 `pos+1` 次"。

### ⚠️ 实测的两个真实缺陷（我写了探针跑出来的，不是猜的）

探针输出（原样，`[三节点]` = 1→3→4）：

```
[三节点] size=3 倒数第1=HeroNode [no=4, ...]        ✅ 正确
[三节点] 倒数第3=HeroNode [no=1, ...]               ✅ 正确
[三节点] 倒数第4(越界)=null                         ✅ 合理
[单节点] size=1 倒数第1=null                        ❌ 错！应该是它自己
链表为空
[空链表] 倒数第0 抛异常: java.lang.NullPointerException  ❌ 崩
[三节点] 倒数第0=null                               ⚠️ 语义未定义（index 从 1 起才算数）
```

**缺陷 1：单节点链表取"倒数第 1 个"返回 `null`。** 罪魁祸首是这个守卫条件：

```java
if (pos < 0 || temp.next == null) return null;
```

只有一个节点时 `pos = 1 - 1 = 0`（本该原地返回），可 `temp.next == null` 也成立，于是被误判成"没找到"。这个条件把"**链表只剩一个节点**"和"**没找到**"混为一谈了。

**缺陷 2：空链表传 `index = 0` 直接 NPE。** `temp = head.next` 是 `null`，`pos = 0 - 0 = 0` 不小于 0，守卫短路失效，接着执行 `temp.next` → 在 `null` 上取字段 → `NullPointerException`。

修法（只动逻辑不动结构）：

```java
public static HeroNode findLastIndexNode(HeroNode head, int index) {
    int size = getLength(head);
    if (index < 1 || index > size) return null;   // ★ 先把非法入参挡掉，别让 temp 变成 null 再解引用
    HeroNode temp = head.next;
    for (int i = 0; i < size - index; i++) temp = temp.next;
    return temp;                                   // 单节点 + index=1 时循环 0 次，直接返回它自己
}
```

要点：**边界校验要在"解引用"之前做完**，别让 `temp` 有机会是 `null`。

### 延伸：快慢指针，一次遍历搞定（面试加分项）

两次遍历要跑 `2n`。让两个指针先拉开 `index` 的间距，一起往前走，快的到 `null` 时慢的正好在倒数第 index 个：

```
   先走 index 步：  slow ▲                        fast ▲
   [head]→[1]→[3]→[4]→null        间距固定 = index
                    然后同时走：  slow 停在倒数第 index 个，fast 撞 null
```

时间 O(n)、空间 O(1)、**只遍历一遍**，而且天然不需要 `getLength`（顺带绕开了上面那两个坑）。它还是"判断链表有没有环"的同一把钥匙（第十四节延伸）。

## 七、反转：头插法，每一步都能逐帧看

这部分**内容太多，别在这儿读**——直接打开 [单链表反转动画.html](./单链表反转动画.html)（双击即可，纯离线、无外部依赖），它按你代码的执行顺序逐帧驱动，橙色线=刚改写、绿色线=已完成、灰色虚线=中途失效的 `head.next`，右侧代码高亮 + 指针变量表同步跳动。这里只留骨架。

```java
while (temp != null) {
    next = temp.next;                   // ① 存后路
    temp.next = reverseHead.next;       // ② 连到"新链表当前的最前面"
    reverseHead.next = temp;            // ③ 哨兵指向它，它成了新的第一个
    temp = next;                        // ④ 迈步
}
head.next = reverseHead.next;           // ⑤ 接回原哨兵
```

```
   生活类比：一串钥匙按 1-3-4 挂着，从前往后一枚枚取下，每次都插到最前面 → 取完变 4-3-1
              「插到最前面」这个动作本身就是反转

   实测结果（当前 main 跑出来的）：head → 4 林冲 → 3 吴用 → 1 宋江 → null ✅（2 号节点已被 delete 摘掉，所以只剩三个）
   全程只 new 了一个空哨兵 reverseHead，数据节点一个都没新建 → 空间 O(1)
```

三个必须记住的点：

1. **节点本体不搬家，只有 `next` 被重连。** 数组反转要真的交换数据，链表只改指针。
2. **`temp` / `prev` 这类指针变量只是"书签"**，`temp = temp.next` 不会移动任何节点。
3. **顺序铁律**：① 必须在 ② 之前（否则后路被抹掉），② 必须在 ③ 之前（否则 `temp.next = reverseHead.next` 拿到的 `reverseHead.next` 已经是 `temp` 自己 → **自环死循环**）。动画里"坑1/坑2"两个按钮就是专门演示这两种翻车，实测：坑1 让 3、4 变成再也找不回的孤链，坑2 让节点指向自己。

对照另一种主流写法（三指针原地反转，动画里可切换）：

| | 头插法（本代码） | 三指针原地反转 |
|---|---|---|
| 额外 new | 一个 `reverseHead` 哨兵 | 0 个，纯指针变量 |
| 直觉 | "插到最前面 = 颠倒" | "箭头原地掉头" |
| 时间/空间 | O(n) / O(1) | O(n) / O(1) |
| 递归版 | 空间 O(n) 栈，长链表会 `StackOverflowError`，不推荐 ||

## 八、`reversePrint`：借栈的后进先出（不改动原链表）

```java
Stack<HeroNode> stack = new Stack<>();
while (temp != null) { stack.push(temp); temp = temp.next; }   // 只读 next，不写 next
while (stack.size() > 0) System.out.println(stack.pop());
```

```
   链表 1 → 2 → 3 → 4   逐个压栈          栈（顶在上方）      弹出顺序
                                            ┌───┐
                                            │ 4 │  ← 顶
                                            ├───┤
                                            │ 3 │
                                            ├───┤
                                            │ 2 │
                                            ├───┤
                                            │ 1 │
                                            └───┘      4 → 3 → 2 → 1
```

关键对比 —— **为什么不破坏原链表**：全程只执行 `temp = temp.next`（读），没有一句 `X.next = ...`（写）。而第七节的反转是**真的改指针**，所以 `main` 里那两行标题写得准确：`单链表反转(影响原链表)` vs `逆序打印单链表(不改变原链表)`。

两者正好互逆，这一点在实测输出里直接体现：`delete(2)` 放开后链表是 `1→3→4`，反转成 `4→3→1`，紧接着 `reversePrint` 又打出 `1→3→4` ✅ 与反转前的顺序一模一样，互逆得到实证。

三种"逆序看"的做法对比：

| 做法 | 时间 | 空间 | 是否改动原链表 |
|---|---|---|---|
| 栈（本代码） | O(n) | **O(n)** | ❌ 不改 |
| 先反转 → 打印 → 再反转回来 | O(n)×3 | O(1) | ✅ 改两次（中途异常会留下乱链） |
| 递归 `print(node.next)` 后再打印 | O(n) | O(n) 调用栈 | ❌ 不改，但长链表会 `StackOverflowError` |

一个小小的顺序瑕疵：`HeroNode temp = head.next;` 写在了 `if (head.next == null) return;` 前面。因为 `head` 是哨兵对象本身不可能为 null，不会 NPE，但读起来是"先用了再验"，建议先判空再声明。

栈本身的规矩、`add` 与 `push` 的关系、JDK `Stack` 的设计缺陷，见 [栈.md](./%E6%A0%88.md)（对应程序 [TestStack.java](./TestStack.java)，它在 `linkedlist` 包里；自己实现的两种栈在 `stack` 包：[ArrayStackDemo.java](../stack/ArrayStackDemo.java) 数组版、[LinkedStackDemo.java](../stack/LinkedStackDemo.java) 链栈版，后者见 [链栈.md](../stack/%E9%93%BE%E6%A0%88.md)）。

## 九、`mergeSortedList`：归并的 merge 过程（本轮修正过一个致命坑）

### 先说前提

**两条链必须各自已经有序**（本代码里靠 `addByOrder` 保证），合并只是把它们织成一条有序链，不需要重新排序。

### 做法：一个哑哨兵 + 一根不断前移的线

```java
SingleLinkedList merged = new SingleLinkedList();
HeroNode cur = merged.getHead();               // cur 始终指合并链的当前尾部
HeroNode p1 = head1 == null ? null : head1.next;   // ★ 跳过硬哨兵，从第一个有效节点开始比
HeroNode p2 = head2 == null ? null : head2.next;
while (p1 != null && p2 != null) {
    if (p1.no <= p2.no) { cur.next = p1; p1 = p1.next; }   // 小的先挂
    else                { cur.next = p2; p2 = p2.next; }
    cur = cur.next;                                        // 合并链长一格
}
cur.next = (p1 != null) ? p1 : p2;              // 剩下那一整段直接接上，不用逐个搬
```

```
   1 → 3 → 5      2 → 4 → 6              merged: (哨兵)
   ↑p1             ↑p2                    ↑cur
   1<=2 → 挂1，p1→3        哨兵 → 1        ↑cur
   3>2  → 挂2，p2→4        哨兵 → 1 → 2    ↑cur
   3<=4 → 挂3，p1→5        哨兵 → 1 → 2 → 3 ...
   ... 直到 p1 走完，p2 手里还剩 6 → 整段挂上：1 → 2 → 3 → 4 → 5 → 6 → null

   注意最后一行：循环退出时两条链最多只可能一条非空，所以是三元表达式而不是两个 if
```

### ⚠️ 你原来那版的致命问题（已实测复现）

原版直接拿传进来的 `head1.no` 做比较，也就是**把 `head` 当数据节点用**；但本项目的 `getHead()` 返回的是 `no=0` 的空壳哨兵。两个习惯一撞就碎：

```
哨兵 A(no=0) 与 哨兵 B(no=0) 比大小 → 0 < 0 为假 → else 分支把【哨兵 B 本体】接进结果链
下一轮 0 < 1 又为真 → 把【哨兵 A 本体】也接进去，并且 cur.next 一路改写下去

探针实测结果（两条原链是 1→3→5 和 2→4→6）：
  原版结果链：0() -> 0() -> 1 -> 2 -> 3 -> 4 -> 5 -> 6 -> null      ← 开头混进 2 个 no=0 空壳
  链a 合并后 list()：1 2 3 4 5 6                                       ← 原本只有 1/3/5，被搅成了六节点混链
```

难就难在：**结果看上去是"有序"的，没报错**，但返回值里躺着两个空壳哨兵，而原链表的哨兵被当成数据节点接走了——链表结构已经坏掉。教训：**一个类里所有方法对"head 是哨兵还是数据节点"必须有统一约定**，`getLength`/`reverseLinkedList` 都吃哨兵，`mergeSortedList` 不能例外。

顺手修掉的三个小问题：`<` 改 `<=`（编号相等时先取链表一，保证**稳定**）；两个 `if` 尾接合成一个三元；返回类型从 `HeroNode` 改成 `SingleLinkedList`，这样能直接用现成的 `.list()` 打印，不必再写第三个打印方法。

### ⚠️ 合并的副作用（实测，必须知道）

合并**不新建数据节点，只改线**，所以两条原链的节点被抽进新链，合并完就不能再用原链表了：

```
合并后 m1 从自己哨兵看：1 → 2 → 3 → 4 → 5 → 6      ← 它"意外得"到了整条合并链
合并后 m2 从自己哨兵看：2 → 3 → 4 → 5 → 6      ← 错位，已经不能看了
```

所以 `main` 里的合并演示专门**新建了两条独立链**，免得把上面反转、逆序打印那几段的结果弄乱。想保留原链，就只能在新链上 `new` 节点复制（代价：空间从 O(1) 变 O(m+n)）。

### 边界用例（全部跑过）

| 用例 | 输入 | 实测结果 |
|---|---|---|
| 编号相等 | 链一 `2(链表一的2)` vs 链二 `2(链表二的2)` | `2(链表一的2) → 2(链表二的2)` ✅ 稳定 |
| 一空一非空 | 空 vs `7 → 8` | `7 → 8`，长度 2、编号递增 ✅ |
| 两条都空 | 空 vs 空 | 结果哨兵 `next == null`，`list()` 打"链表为空"，不抛 ✅ |
| 传 null | `null, null` / `null, 9` | 不抛异常，后者得 `9` ✅ |
| 长短悬殊 | `1` vs `8 → 9 → 10` | `1 → 8 → 9 → 10`，尾段整接生效 ✅ |

## 十、复杂度总账

| 操作 | 时间 | 说明 |
|---|---|---|
| `add` 尾插 | **O(n)** | 每次都要走到尾巴。想 O(1) 就额外存一个 `tail` 指针 |
| `addByOrder` | O(n) | 遍历找位置 |
| `update` / `delete` | O(n) | 按编号找，链表没有"按下标直达" |
| `list` / `getLength` | O(n) | 全遍历 |
| `findLastIndexNode` | O(n)（两次遍历 ≈ 2n） | 快慢指针可到 1 次遍历 |
| `reverseLinkedList` | O(n) | 一次遍历，**会改原链表** |
| `reversePrint` | O(n) | 空间 O(n)（栈），不改原链 |
| `mergeSortedList` | O(m+n) | 空间 O(1)，但会把两条原链的节点抽走 |
| 空间 | O(n) 存 n 个节点 | 反转/合并都只多 O(1) 个指针 |

顺带把 [队列.md](../queue/%E9%98%9F%E5%88%97.md) 那个坑结掉：**用链表实现队列，`front` 出队、`rear` 入队都是 O(1)，而且不存在"假满"** —— 因为没有固定数组，也就没有需要绕圈的下标。环形队列是用"牺牲一格 + 取模"补救数组，链表则是直接把容量问题取消掉。

## 十一、代码里另外几处值得商榷的地方

1. **`getHead()` 的注释和它的用途自相矛盾。** 注释写「返回头节点，**防止直接修改头节点**」，但把可变的 `head` 对象交出去，恰恰允许外部随便改 `head.next` —— 而 `main` 里的反转正是靠 `reverseLinkedList(singleLinkedList.getHead())` 改的。真要防修改，应该把反转、求长度这类算法做成 `SingleLinkedList` 的实例方法，或者返回不可变视图；现在这句注释只是表达了"意图"，没做到"约束"。
2. **`SingleLinkedList` 和 `HeroNode` 都写在了 `SingleLinkedListDemo.java` 里**，靠"一个 .java 只能有一个 public 类"的规则勉强成立。练习无妨，正式项目应各自一个文件。
3. **`getLength` 的 `println` 副作用**（第五节已述），已经在本方法的调用链上污染了 `findLastIndexNode` 的输出。
4. **`findLastIndexNode` 的两处边界缺陷**（第六节实测）。
5. `delete` 之后节点被 GC，但如果链表里存的是**对象引用**，反转/删除时把不再使用的格子置 `null` 是好习惯（JDK `ArrayDeque.poll` 就显式 `elements[tail] = null`），数组版尤其容易留出"忘不掉"的引用。
6. **`mergeSortedList` 与其余方法的"head 语义"不一致**（第九节实测已修正）：这类 bug 不会报错、只会让结果"看上去对"，是链表代码最阴的一种。建议写链表方法时先定一句约定：**入参永远是哨兵 head，比较永远从 `head.next` 开始**。

## 十三、一句话记住单链表

> **每个节点 = 数据 + 一根指向下一个的线；哨兵 head 不存数据、全程不动，为的是让第一个节点不再特殊（也因为 Java 改 `head` 本身外面看不见，只能改 `head.next`）；插入和删除都是"改两根线"，但必须"先接后断"，否则后面的链会永久失联；temp 停在目标的前驱还是目标本身，取决于你要"往它后面动手"还是"改它自己"；反转是头插法（存后路→连前驱→挂牌→迈步），节点不搬家、只重连 next，顺序一步都不能换。**
