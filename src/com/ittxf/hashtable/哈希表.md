# 哈希表（数组 + 链表法解决冲突）

> 对应程序：[HashTableDemo.java](./HashTableDemo.java)（一个文件里四个类：`HashTableDemo` 菜单、`HashTable` 哈希表、`EmpLinkedList` 单向链表、`Emp` 雇员）
> 前置阅读：[单链表.md](../linkedlist/%E5%8D%95%E9%93%BE%E8%A1%A8.md) —— 每个桶里装的就是一条单链表，`add`/`findById` 全是链表那篇里的老动作；本篇的新东西只有"先用散列函数挑桶"这一步。
> 实测环境 JDK 21，跑法见第六节。

---

## 一、一句话：把"找"从 O(n) 变成"先挑桶，再在桶里找"

前面几篇查找都躲不开线性扫描（[搜索算法.md](../search/%E6%90%9C%E7%B4%A2%E7%AE%97%E6%B3%95.md) 里二分要先把数组排好）。哈希表的思路完全不同：**不比较大小，直接用 key 算出该去哪个位置**。

```java
public int hashFun(int id) {
    return id % size;          // 除留余数法
}
```

`add(emp)` = 算出桶号 → 把 emp 挂到那条链表尾部；`findById(id)` = 算出桶号 → 只在那条链表里线性找。**key 相同的记录必然落在同一个桶**，这是整套逻辑成立的前提。

```
   size = 5，依次 add id = 1..10 之后，实测 list() 的输出：

   第1条链表（下标 0）：id=5, id=10          ← 5%5=0、10%5=0
   第2条链表（下标 1）：id=1, id=6
   第3条链表（下标 2）：id=2, id=7
   第4条链表（下标 3）：id=3, id=8
   第5条链表（下标 4）：id=4, id=9
```

"冲突"就是这个画面：**10 个人挤进 5 条链表，每条 2 个人**。散列函数没有消除查找，它只是把一次 10 个的扫描切成两次 2 个的扫描。

## 二、四个类怎么分工

```java
class HashTable {                        // 只管两件事：算桶号、把活派给对应的链表
    private EmpLinkedList[] empLinkedListArray;
    private int size;
    public HashTable(int size) {
        this.size = size;
        this.empLinkedListArray = new EmpLinkedList[size];
        for (int i = 0; i < size; i++) {          // 注释写着"不初始化会报空指针异常"
            this.empLinkedListArray[i] = new EmpLinkedList();
        }
    }
    public void add(Emp emp) { empLinkedListArray[hashFun(emp.id)].add(emp); }
    public Emp findById(int id) { /* 定位桶 → 链表里找 → 打一行结果 → 返回 Emp 或 null */ }
}

class Emp { int id; String name; Emp next; }      // 节点：数据 + 一根后继指针

class EmpLinkedList { private Emp head; ... }     // 头指针，默认 null，表示空桶
```

第 53~56 行那个循环是真需要的：`new EmpLinkedList[size]` 只造出一个装满 `null` 的数组，桶本身还得逐个 new。少了这段，第一次 `add` 就会在 `empLinkedListArray[hashFun(id)].add(emp)` 上抛 NPE（对着 null 调方法）—— 这句就是代码注释里"不初始化会报空指针异常"的来历。

## 三、`EmpLinkedList` 的三个方法，和链表那篇的差别

| 方法 | 做法 | 代价 | 注意 |
|---|---|---|---|
| `add` | `head == null` 就直接挂头；否则 while 走到尾巴再 `temp.next = emp` | **O(链长)** | 是遍历到尾再挂，不是头插。第 111~112 行的注释"假定添加雇员时 id 是自增长…直接加入到本链表的最后"是**假设**，代码里没有强制（下一节实测打破它） |
| `list(no)` | 空桶打"第N条链表为空"；否则 `print` 表头 + 逐个 `println` | O(链长) | `no + 1` —— 打印的是人类的第几条，数组下标从 0 起 |
| `findById` | `while (temp != null)`，命中就 `break`，返回 `temp` | 最坏 O(链长) | 靠 `temp` 是否为 null 同时表达"命中"和"没命中"，所以末尾 `return temp` 一句就够 |

**桶数决定代价**：`HashTable(5)` 装 10000 个雇员，每条链表就是 2000 个节点，`findById` 平均要走 1000 步 —— 跟没有哈希表几乎一样。同一批数据如果桶开到 1000，每条链 10 个人，平均 5 步。散列函数的意义就在于**把 n 个人的开销平摊到 k 条链上**（`n/k`），`k` 太小就退化回链表。这份实现的 `size` 是构造时写死的 5，既没有 rehash，也没有负载因子的概念。

## 四、⚠️ 实测到的两个边界

### 1）负 id 直接越界

```java
public int hashFun(int id) { return id % size; }   // size = 5
```

Java 的 `%` 结果**跟着被除数的符号**：`-1 % 5 = -1`（不是 4）。实测：

| 调用 | 结果 |
|---|---|
| `add(new Emp(-1, "负号"))` | `ArrayIndexOutOfBoundsException` —— `empLinkedListArray[-1]` |
| `findById(-1)` | `ArrayIndexOutOfBoundsException` —— 同一个位置 |

也就是说这套 API 只接受**非负 id**。真要接住负数，散列函数得写成 `Math.floorMod(id, size)`（或者 `(id % size + size) % size`）。

### 2）"id 自增"这个假设一旦不成立，桶里顺序就乱了

代码注释把"id 总是从小到大"当前提，实测先加 15 再加 10（两个都落第 1 条链，因为 `15 % 5 = 10 % 5 = 0`）：

```
第1条链表中的数据：id=15, name=十五
                  id=10, name=十
```

**链表顺序是插入顺序，不是 id 顺序。** 好消息是 `findById(10)` 照样能找到（它本来就是线性扫描，不依赖有序）；坏消息是任何"以为桶里是有序的"想法都不成立。真正需要顺序的是红黑树那种结构 —— JDK 8 的 `HashMap` 在**某个桶的链表长度达到 8 且表长 ≥ 64** 时才会把这条链换成红黑树（表长不够就先扩容），换树的前提是 key 可比较。

另外 `id = 0` 是合法的：`0 % 5 = 0` → 落第 1 条链表，实测 `findById(0)` 打印"在第1条链表中找到雇员：0，零号"。而 `findById(99)`（不存在）打印"id=99的雇员不存在该哈希表中"并返回 `null`。

### 3）这套 API 只有 `add` / `list` / `findById`

没有 `delete`。这不是遗漏，是**删除确实是哈希表里更麻烦的一件事**：链表版删一个节点要接前后指针（正好接上[双向链表.md](../linkedlist/%E5%8F%8C%E5%90%91%E9%93%BE%E8%A1%A8.md)说的"由被删节点自己摘自己"）；如果用开放定址法，删完还得留一个"已删除"标记，否则探测链会断。

## 五、和其它查找方式的对照

| | 结构 | 前提 | 一次查找 | 空间 |
|---|---|---|---|---|
| 线性查找 `SeqSearch` | 数组 | 无 | O(n) | O(1) |
| 二分/插值/斐波那契 | 数组 | **必须有序** | O(log n) / 期望 O(log log n) | O(1) |
| 二叉排序树 | 树 | 维持不变式 | 平均 O(log n)，退化 O(n) | O(n) 指针 |
| **本篇哈希表** | 数组 + 链表 | key 能算出桶号 | 平均 O(1 + n/k)，最坏 O(n) | O(n + k) |
| JDK `HashMap` | 数组 + 链表/红黑树 | `hashCode()` + `equals()` | 平均 O(1)（链长 > 64 且表长 ≥ 64 转树） | O(n) |

一句提醒：哈希表**放弃了顺序**。"找出所有 id 在 [10, 20] 的雇员"这种范围查询，哈希表只能全表扫，而有序数组/TreeMap 可以直接定位区间 —— 这也是 [搜索算法.md](../search/%E6%90%9C%E7%B4%A2%E7%AE%97%E6%B3%95.md) 第十一节把"哈希 vs 平衡树"列为对照的原因。

## 六、动手验证剧本

`main` 是命令行菜单，跑起来按提示输入：

```powershell
javac -encoding UTF-8 -d out src\com\ittxf\hashtable\HashTableDemo.java
java -cp out com.ittxf.hashtable.HashTableDemo
# add → 1 → 宋江 ；add → 6 → 吴用 ；list ；find → 6 ；find → 99 ；exit
```

也可以一次性把整串操作喂给标准输入（实测有效，输出里 `find 6` 那步打印的是"在第2条链表中找到雇员：6，吴用"）：

```powershell
"add`n1`n宋江`nadd`n6`n吴用`nlist`nfind`n6`nfind`n99`nexit" | java -Dstdout.encoding=UTF-8 -cp out com.ittxf.hashtable.HashTableDemo
```

| 实验 | 怎么做 | 会看到什么 | 印证哪一节 |
|---|---|---|---|
| 1 | add id = 1..10，然后 `list` | 5 条链表各 2 人，第 1 条是 5、10 | 一节 |
| 2 | `find` 输入 7 | "在第3条链表中找到"（`7 % 5 = 2`，打印时 +1） | 二节 |
| 3 | `find` 输入一个没加过的 id | "…不存在该哈希表中" | 三节 |
| 4 | 把构造参数 `5` 改成 `1` | 所有 id 挤进同一条链，`list` 打出一条 10 个节点的长链 —— 哈希表退化成链表 | 三节 |
| 5 | add id = 15 之后再 add id = 10 | 第 1 条链是 `15, 10`，按插入顺序 | 四节 2） |
| 6 | add id = 0 | 落进第 1 条链表，不报错 | 四节 |

第 4 条最建议跑：把桶改成 1，就亲眼看到"散列函数没起作用时哈希表就是链表"。

## 七、一句话记住哈希表

> **哈希表 = 数组 + 一个"由 key 直接算下标"的函数；冲突用链表挂在那个位置上，所以查找代价是"1 次取模 + 桶内线性扫描"，桶越多每条链越短（`n/k`），桶数写死又从不 rehash 的实现会在数据一多时退化成链表；`id % size` 在负数上会得到负下标（Java 的 `%` 跟被除数同号），要接负数得用 `Math.floorMod`；"插入的 id 一定递增"只是注释里的假设，实测先 15 后 10 就会让桶内顺序变成插入顺序；这套 API 只做了增/查/遍历，删除留作下一课。**

## 八、往下学什么

1. **开放定址法**：不建链表，冲突了按规则找下一个空位（线性探测 / 二次探测 / 双重散列），代价是"删除要留墓碑"，收益是缓存友好。
2. **负载因子与 rehash**：`n/k` 越过阈值就把表翻倍重算 —— 这是把第三节那笔"桶数写死"的账彻底解决掉，JDK `HashMap` 的 0.75 就是这么用的。
3. **散列函数怎么选**：`id % size` 里 `size` 取质数能显著减少聚集；字符串一般先 hash 再取模（对照 JDK `String.hashCode()`）。
4. **桶太长换树**：JDK 8 的 `HashMap` 链长到 64 且表长 ≥ 64 时转红黑树，正好把 [二叉树.md](../tree/%E4%BA%8C%E5%8F%89%E6%A0%91.md) 和本篇接起来 —— 树负责"链太长时别退化"，哈希负责"平时一步到位"。
5. **回到那两篇**：为什么"哈希查找 O(1)"和"范围查找"不可兼得，看 [搜索算法.md](../search/%E6%90%9C%E7%B4%A2%E7%AE%97%E6%B3%95.md) 第十一节；链表部分的增删细节全在 [单链表.md](../linkedlist/%E5%8D%95%E9%93%BE%E8%A1%A8.md)。
