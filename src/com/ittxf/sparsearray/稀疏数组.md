# 稀疏数组

> 对应程序：[sparseArray.java](./sparseArray.java)
> 这份代码干了三件事：二维数组 **→** 稀疏数组 **→** 存到磁盘文件 `filePath/map.data` **→** 读回来 **→** 恢复成二维数组。压缩和持久化一起练了。

## 一、先说人话：稀疏数组是个什么东西

一句话：**一个表格里绝大多数格子都是同一个废话值（通常是 0），我就只记"哪些格子有东西、是什么东西"，那些 0 一律不存。**

拿代码里的五子棋棋盘举例（11×11 = 121 个格子，实际只落了 2 颗子）：

```
          col0 col1 col2 col3 col4 col5 ... col10
        ┌────┬────┬────┬────┬────┬────┬───┬────┐
 row0   │  0 │  0 │  0 │  0 │  0 │  0 │...│  0 │
 row1   │  0 │  0 │ ●1 │  0 │  0 │  0 │...│  0 │  ← 黑子在 (1,2)
 row2   │  0 │  0 │  0 │ ○2 │  0 │  0 │...│  0 │  ← 白子在 (2,3)
 row3   │  0 │  0 │  0 │  0 │  0 │  0 │...│  0 │
 ...    │    全部是 0，纯纯占地方的占位符           │
 row10  │  0 │  0 │  0 │  0 │  0 │  0 │...│  0 │
        └────┴────┴────┴────┴────┴────┴───┴────┘

  存下来要 121 个数，其中有用的只有 2 个 → 98.3% 的空间在记「这里啥也没有」
```

太浪费了。于是换个记账方式：**别记"哪没有"，只记"哪里有"**。

```
稀疏数组长这样（列固定 3 个：行、列、值）

  ┌──────────┬──────┬──────┬──────┐
  │  下标    │ row  │ col  │ val  │
  ├──────────┼──────┼──────┼──────┤
  │  [0]     │  11  │  11  │   2  │  ← 第 0 行是"说明书"：原数组 11 行 11 列，共 2 个非零值
  │  [1]     │   1  │   2  │   1  │  ← 第 1 行第 2 列 = 1（黑子）
  │  [2]     │   2  │   3  │   2  │  ← 第 2 行第 3 列 = 2（白子）
  └──────────┴──────┴──────┴──────┘

  尺寸：int[sum + 1][3]   ← 代码里就是这个，sum 是非零元素个数，+1 是留给说明书那行
```

两边一映射，关系一目了然：

```
  原始二维数组                    稀疏数组
  (1,2) = 1      ──────────►    [1] │ 1  2  1
  (2,3) = 2      ──────────►    [2] │ 2  3  2
  行数 11、列数 11 ──────────►   [0] │ 11 11 2      ← 没有这一行，读回来时不知道要开多大的数组
  其余 119 个 0  ──────────►    （不存，省掉）
```

**空间账**：`121 × 4B = 484B` → `3 × 3 × 4B = 36B`，直接干掉九成多。棋子越多省得越少，这是下面第七节要聊的代价。

## 二、第 0 行为什么是"必须有"的（重点）

新手最容易忽略这行的价值。它不是装饰，它是**还原的钥匙**：

```java
sparseArr[0][0] = 11;              // 原数组行数
sparseArr[0][1] = 11;              // 原数组列数
sparseArr[0][2] = sum;             // 非零元素个数
```

恢复的时候第一件事就靠它：

```java
int[][] chessArr2 = new int[sparseArrFromFile[0][0]][sparseArrFromFile[0][1]];
```

如果没有第 0 行，你手里只剩一堆 `(row, col, val)` 三元组，**根本不知道原来的棋盘是 11×11 还是 100×100**。同理，`sum` 那一位让你不数行数就知道后面要读几条数据。

> 记住一句话：**稀疏数组 = 尺寸说明书 + 非零明细表**。

## 三、正向：二维数组 → 稀疏数组（三步）

对应代码 [第 24-53 行](./sparseArray.java#L24-L53)。

```
第 1 步：先扫一遍，数出非 0 的个数 sum          第 2 步：按 sum 开稀疏数组，填说明书
   ┌──┬──┬──┐                                  ┌────┬────┬────┐
   │0 │0 │0 │                                  │ 11 │ 11 │ 2★ │ ← sparseArr[0]
   ├──┼──┼──┤   遍历 121 个格子                   ├──┼────┼────┤
   │0 │0 │1★│   遇到 !=0 就 sum++                 │  │    │ 0  │ ← 还没填
   ├──┼──┼──┤   得到 sum = 2                     ├──┼────┼────┤
   │0 │0 │0 │        │                          │  │    │ 0  │
   └──┴──┴──┘        ▼ 第 3 步再扫一遍填充
                int[sum+1][3] = int[3][3]
```

三步走的代码骨架：

```java
// 1 遍历统计非 0 个数
int sum = 0;
for (int i = 0; i < 11; i++)
    for (int j = 0; j < 11; j++)
        if (chessArr[i][j] != 0) sum++;

// 2 开稀疏数组 + 写第 0 行说明书
int[][] sparseArr = new int[sum + 1][3];
sparseArr[0][0] = 11; sparseArr[0][1] = 11; sparseArr[0][2] = sum;

// 3 再遍历一次，遇到非 0 就按顺序落到 sparseArr[count]
int count = 0;
for (int i = 0; i < 11; i++)
    for (int j = 0; j < 11; j++)
        if (chessArr[i][j] != 0) {
            count++;                              // 先 ++，因为 [0] 已被说明书占了
            sparseArr[count][0] = i;
            sparseArr[count][1] = j;
            sparseArr[count][2] = chessArr[i][j];
        }
```

两个细节值得盯一下：

- **为什么要遍历两遍？** 因为不先扫一遍就不知道 `sum`，不知道 `sum` 就开不出正确大小的数组。这是「先数后填」套路，不是写复杂了。想只扫一遍得用 `ArrayList`（见第五节读文件那边用的就是这招）。
- **`count++` 放在赋值前面**：因为下标 0 已经被第 0 行占了，第一个真实数据必须落在 `sparseArr[1]`。这个顺序写反了会覆盖说明书，症状是恢复出来的数组行列数变成第一个棋子的坐标，非常诡异。
- 循环里的 `11` 是**硬编码**的，更稳的写法是 `chessArr.length` 和 `chessArr[0].length`，换棋盘尺寸就不用改三处数字。

## 四、反向：稀疏数组 → 二维数组（两步）

对应代码 [第 74-93 行](./sparseArray.java#L74-L93)。注释里其实已经把这方法总结成两句话了，就是这个顺序：

```
① 读第 0 行 → 知道原数组多大 → new int[rows][cols]（此时全 0，天然就是"空格子"）
② 从第 1 行起，逐条把 val 塞回 chessArr[row][col]

  sparseArr                 chessArr2
  [0] 11 11 2  ──► 开一个 11×11 的全 0 数组
  [1]  1  2 1  ──►    ┌────┬────┬────┐
  [2]  2  3 2  ──►    │ .. │ .. │ ●1 │  row=1,col=2 → 填 1
                      │ .. │ .. │ .. │ ○2 │  row=2,col=3 → 填 2
                      │ 其余全是 0，不用管，第①步已经是 0
                      └────┴────┴────┘
```

```java
int[][] chessArr2 = new int[sparseArrFromFile[0][0]][sparseArrFromFile[0][1]];
for (int i = 1; i < sparseArrFromFile.length; i++) {          // ← 注意 i 从 1 开始
    chessArr2[sparseArrFromFile[i][0]][sparseArrFromFile[i][1]] = sparseArrFromFile[i][2];
}
```

大白话：**第①步已经把整个棋盘铺成 0 了，第②步只需要"点上棋子"**，不需要处理 0 —— 这正是稀疏数组压缩的本质：0 是免费得到的默认值。

`i` 从 **1** 开始，跳过第 0 行说明书，否则拿 `11, 11, 2` 当坐标去写 `chessArr2[11][11]`，直接 `ArrayIndexOutOfBoundsException`。

## 五、顺带练的持久化：把稀疏数组写进文件

这是这份代码的第二层价值 —— 数据结构 + 文件 IO 混着练。

### 文件格式（`filePath/map.data`，制表符分隔的纯文本）

```
11	11	2
1	2	1
2	3	2
```

三行文本 = 稀疏数组的三个三元组，肉眼可读、手改可行、其他语言也能解析。比 Java 序列化（`ObjectOutputStream`）那种二进制格式透明得多。

```java
try (BufferedWriter writer = new BufferedWriter(new FileWriter(filePath))) {
    for (int[] row : sparseArr) {
        writer.write(row[0] + "\t" + row[1] + "\t" + row[2]);
        writer.newLine();
    }
}
```

### 读回来：行数不知道，所以先动态收集

```
 文件流              逐行 split("\\t")           ArrayList             int[][]
 "11 11 2" ──► [11, 11, 2] ──► add ──┐
 "1 2 1"    ──► [1, 2, 1]   ──► add ──┤  toArray(new int[0][])  ──► 定长二维数组
 "2 3 2"    ──► [2, 3, 2]   ──► add ──┘
```

```java
while ((line = reader.readLine()) != null) {      // 标准读法：赋值 + 判空一步搞定
    String[] parts = line.split("\\t");           // split 收的是【正则】，所以 \t 要写两对反斜杠
    if (parts.length == 3) { ... dataList.add(data); }
}
sparseArr = dataList.toArray(new int[0][]);       // 传 new int[0][]，底层会帮你按 size 开一个正好大的新数组
```

三个 IO 知识点：

| 点 | 说明 |
|---|---|
| `FileWriter/FileReader` 是**节点流**（直接怼文件），`BufferedWriter/BufferedReader` 是**处理流**（加缓冲、能 `readLine` 按行读），项目统一用「节点流 + 缓冲流」这套字符流组合 |
| **try-with-resources**（`try ( ... )`）自动帮你 `close()`，不用手写 finally，异常也不会漏掉关流 |
| `split("\\t")` 不是字符串字面量而是正则，写成 `split("\t")` 在某些场景（如制表符被吃掉的系统）会不稳；顺带 `trim()` 一下更保险 |

**⚠️ 相对路径的坑**：`String filePath = "filePath/map.data"` 是相对于**运行时工作目录**的，不是相对于源码文件。IDEA 里默认工作目录是项目根 `E:\Code\fullstack\dataStructures\dataStructures`，命令行 `java -cp out ...` 在哪儿执行就取决于哪儿。目录不存在时 `FileWriter` 会抛 `FileNotFoundException`（只创建文件，**不会**帮你创建 `filePath\` 这层目录）。

## 六、⚠️ 这份代码留了一个真实隐患（值得当成反面教材）

读文件和恢复这两步的衔接有问题：

```java
public static int[][] loadSparseArrFromFile(String filePath) {
    int[][] sparseArr = null;
    try (...) { ... }
    catch (IOException e) {
        System.err.println("从文件读取稀疏数组时发生错误: " + e.getMessage());
        e.printStackTrace();       // 打印完就【吞掉】了，没有重新抛出
    }
    return sparseArr;              // ← 失败时返回 null
}
```

```
文件不存在 / 读失败
      │
      ▼
load 内部 catch 掉，打印一句错误，return null
      │
      ▼
main 拿到 null，继续往下跑（它压根不知道出事了）
      │
      ▼
sparseArrFromFile[0][0]  ──►  NullPointerException 💥 没有任何 try 包住，程序崩
```

问题不在于「有没有捕获异常」，而在于**捕获完没有把失败信号传出去**：

- 方法签名没写 `throws IOException`，main 里也就没法 try-catch —— 调用方被剥夺了知情权。
- 用 `null` 当"失败标记"是最容易被忽略的标记，编译器不会提醒你。
- 最终崩在一个跟原始错误八竿子打不着的位置（`new int[...]`），排查时你只会看到 NPE，得往回翻日志才发现真正原因是文件没找到。**这叫「异常延迟爆炸」，比当场炸难查十倍。**

### 两种改法

```java
// 方案 A：上抛，让 main 决定怎么处理（推荐，跟 ArrayQueueDemo 的「方法抛 + 调用方 catch」一致）
public static int[][] loadSparseArrFromFile(String filePath) throws IOException {
    try (BufferedReader reader = new BufferedReader(new FileReader(filePath))) { ... }
}

// main 里
try {
    int[][] data = loadSparseArrFromFile(filePath);
    // 恢复逻辑
} catch (IOException e) {
    System.out.println("读档失败，改用内存数据继续：" + e.getMessage());
}
```

```java
// 方案 B：就地转成非受检异常，让它在调用点立刻炸，不返回 null
catch (IOException e) {
    throw new UncheckedIOException("读取稀疏数组失败: " + filePath, e);   // 保留原始 cause
}
```

顺带两个小清理：`loadSparseArrFromFile` 里那两句 `System.out.println(Arrays.toString(data))` / `Arrays.deepToString(sparseArr)` 是调试输出，正式演示时该删；`parts.length == 3` 不满足时**静默跳过该行**，坏文件会被"悄悄读短"，至少该警告一句。

## 七、代价与适用边界（别把稀疏数组当万能压缩）

天下没有免费的午餐，省空间是拿别的东西换的：

| 换到的 | 付出的 |
|---|---|
| 空间：`rows × cols` → `(sum + 1) × 3` | **两次完整遍历**（正向）才能建出来 |
| 存储/传输的数据量骤降 | **丢掉了一维随机访问**：原来 `arr[1][2]` 一句就取到，现在得去表里找「row=1 且 col=2」的那条，线性 O(sum)（想快得额外建索引/二分） |
| 结构直观、易序列化 | **多存了坐标**：每个非零值要多背 2 个数（row、col） |

### 什么时候会**反而变大**？

拿账算：存一个非零值要花 **3** 个数。原数组一个格子只花 **1** 个数。

```
非零元素占比 p：
  稀疏数组花   sum × 3 ≈ p × rows × cols × 3
  原数组花     rows × cols × 1

  →  p > 1/3  时，稀疏数组开始亏本（还没算第 0 行那 3 个额外开销）
```

```
 格子总数 121，看非零元素多少个才划算：

   2 个  ► 稀疏 9 个数   ✅ 省 92%
  40 个  ► 稀疏 123 个数  ⚠️ 已经亏了
 121 个  ► 稀疏 366 个数  ❌ 胖了 3 倍
```

所以判断标准很简单：**0（或同一个值）占绝对多数，才值得上稀疏数组。**

## 八、真实世界里谁会用它

代码里是五子棋存档，实际用途远不止：

- **棋类/游戏地图存档**：五子棋、扫雷、 minesweeper、大片空的战场地图、Game of Life 生命游戏
- **图像处理**：扫描件背景、天文图像、医学影像里大量像素是同一个值
- **科学计算的稀疏矩阵**：有限元分析、PageRank、推荐系统的用户-物品评分矩阵（百万维、绝大部分是 0），MATLAB/SciPy 里 `scipy.sparse` 就是这一家子
- **数据库**：MySQL 的稀疏索引、MongoDB 里文档字段缺失的索引，思路同源
- **文本统计**：词袋模型文档-术语矩阵，一行几万列，非零只有十几个

## 十、一句话记住稀疏数组

> **稀疏数组 = 「原数组多大 + 有几个非零」的说明书（第 0 行） + 「在哪、是什么」的明细表（后 sum 行）；压缩的本质是"0 不配拥有记录，它是恢复时免费拿到的默认值"；代价是失去随机访问、且非零超过三分之一就亏本；而读档失败时返回 `null` 让主流程继续跑，会把你引向一个更难查的 NullPointerException。**
